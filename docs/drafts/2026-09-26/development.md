## 非公開開発への方針変更（2026-09-26）

ユーザーが「プロジェクトが一定レベルまで完成度が高まるまでプライベートで進める」と指定しました。格納直前の確認では `orbit-remapper` はprivate、`hid-remapper` はpublicです。

今回のドラフトと成果物はprivateの製品リポジトリへ格納します。公開側のHID Remapperリポジトリにはコード・文書・Issue・PRなどの独自成果を追加しません。HID Remapper側の独自実装を始める際は、履歴を保持した独立privateリポジトリなど、非公開の開発先を用意してから進めます。その作業先の作成は今回の資料格納では実施していません。

公開の時期と対象範囲は未決定です。ドラフトの承認・マージを、一般公開への承認と同一視しません。

## 将来の公開に向けて（2026-09-26）

ユーザーが「将来オープンソースとして公開する前提で開発する」と指定しました。公開までは private のまま開発します。

- **公開できない物をこのリポジトリの履歴に入れない。** 公開すると、削除済みのファイルも履歴から見えます。非公開の原本（元BOM、引き継ぎ文書、設計レビューPDF）は private の `techmech-keeb/keyboard-hardware` の `products/orbit-remapper/` に置きます。第三者の素材（メーカー画像、フォント）はどこにも保存せず、出典のリンクだけを残します。生成物（STL、描画、ビューア）は Release に添付します。詳細は[成果物一覧](artifacts.md)。
- **公開の方法（提案）。** Draft PR #1（`docs/draft-design-record-20260926`）には仕分け前の全ファイルが入っています。GitHub の PR の参照は利用者側で削除できないため、このリポジトリをそのまま public にすると PR #1 経由で非公開の原本も見えてしまいます。公開するときは、`main` の履歴だけを新しい public リポジトリへ push する方法を基本とします。このリポジトリを直接 public にするなら、事前に GitHub サポートへ PR #1 の削除を依頼する必要があります。
- **ライセンス。** ソフトウェア・ハードウェア・文書のライセンスは公開前に決めます（open-questions Q17）。

将来の候補: `firmware/s3/`、`hardware/pcb/`、`hardware/enclosure/`、`hardware/bom/`、`docs/protocol/`、`docs/decisions/`、`tests/`、`tools/`。

S3部分は当面製品側に置きます。他製品への再利用や独立したリリース周期が必要になれば、第三のリポジトリへの分離を再評価します。

## 変更管理

- 安定した基準ブランチから短期間の作業ブランチを作り、変更目的ごとにPRを作る。
- 二つのリポジトリにまたがる変更はPRを相互リンクする。
- 製品課題は製品側、HID Remapper固有の変更はフォーク側のIssueに記録する。
- GitHub Projectを一つ作り、両リポジトリの課題をまとめる案。
- 上流更新は専用PRで確認する。単に最新版だから採用した扱いにしない。

## 動作する組み合わせを固定する

製品Releaseに、基板版、筐体版、HID Remapperの完全コミットSHA、S3ソースの版、通信仕様版、依存関係、試験結果を対応付ける案です。指定SHAから取得するビルド補助で始め、独自submoduleの追加は必須にしません。上流が用いるsubmoduleは維持します。

通信仕様の正本は製品側、両ファームに対応仕様版を明記する案。現時点で通信仕様v1が成立したわけではありません。ビルド成功と実機試験の合格は区別します。

## 成果物とライセンス

編集元CADと生成ソースを保存し、検証済みのSTEP/STL/Gerber/バイナリを将来のReleaseに添付する方針。今回のSTEP/STLは履歴保存用の試作候補です。Release・製造用ディレクトリへ昇格していません。

元BOM XLSXは原本を保存。今回作ったCSVはシート内容の参照用書き出しであり、新しい正本ではありません。将来CSVを正本とする提案と、今回の保存処理を区別します。

大きなバイナリCADの更新が増えた段階でGit LFSを検討。今回LFS移行は行いません。

上流READMEはソフトウェアMIT、ハードウェアCC BY 4.0（別記のない場合）と説明しています。個別ファイルと依存物の通知を維持します。新規設計・文書・メーカー参照画像を一括してMITと宣言することはしていません。保存したIPAフォントのライセンス文書も同梱します。[出典](sources.md)

## ドラフトから確定版へ

1. 各文書にある未確定事項を確認し、ユーザーが決めた内容と検証した内容を記録する。
2. 対象文書・構成・版・日付を指定して「何が確定したか」を記録する。
3. 確定する内容を正式な文書の置き場へ整理する。履歴スナップショットは残す。
4. 成果物を更新する場合、対応するBOM・機構・ファーム・試験版を記録する。
5. 製造承認は文書の確定と別に、現物・公差・電気・組立など必要な確認結果に基づき扱う。

ユーザーの「確定してから最終化」の指示に沿い、今回のPRはDraftで作成します。後でドラフト資料をmainへ保存する場合も、マージだけで本文のstatusや承認状態を確定扱いへ変えません。
