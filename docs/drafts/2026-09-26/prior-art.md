## esp32-hid-gamepad-bridge

ESP-IDF の BLE HID ホスト機能で、BLE のキーボードとマウスを同時に受ける実装。作者は ESP-IDF の不具合を実機で追いかけた記録を `AGENTS.md` 第 4 章に残している。D 案（M5Dial 単体）で BLE 受信を作る場合に、そのまま当てはまる内容が多い。

| 項目 | 内容（`AGENTS.md` の記述） | Orbit への影響 |
| --- | --- | --- |
| §4.33 | `esp_hidh` が接続時に条件を指定しない（NULL）ため、NimBLE の初期値の接続間隔 30〜50 ms になり、報告は 20〜33 Hz しか届かない | 接続後に間隔を短くする要求が必要 |
| §4.33 | ESP32-C3 と S3 で、自分から 15 ms より短い間隔を要求すると断られた（HCI 0x12）。機器の側が 7.5 ms を求めた接続は、そのまま維持された | 下記「接続間隔の下限は未確定」を参照 |
| §4.2 | ESP-IDF の BLE HID の機器側（hidd）とホスト側（hidh）を同時に使うと設定を上書きし合う | Orbit は PC へ USB で出すので避けられる |
| §4.11 | 機器を開く関数（`esp_hidh_dev_open()`）の呼び出し元に大きなスタックが必要 | 設計時の注意 |
| §4.15 | NimBLE 経由では機器の種類が常に「汎用」と返る | キーボードかマウスかはレポート記述子から判断する |
| §4.20 | スリープから復帰したキーボードは、HID の識別子（UUID 0x1812）を出さずに接続を求める | 識別子で絞り込んで探すと再接続できない |
| §4.23 / §4.25 | 機器を開く処理が永久に止まることがある。切断を知らせるイベントが届かない | スリープ後に機器が戻らない原因 |
| §4.27 / §4.28 | 再接続時に内部状態がリセットされず落ちる。NimBLE 内部の配列の大きさの取り方が誤っていて落ちる | 複数台の抜き差しで落ちる原因 |
| §4.29 | `esp_hidh` は暗号化を自分から始めない。HOGP は暗号化が前提なので、機器によっては「つながるのに入力が来ない」 | 一部のマウスで発生 |
| §4.34 | ペアリング前の機器で無効なアドレスに書き込む | 設計時の注意 |
| §4.35 | ペアリングの成否が BLE 回路の世代で変わる（C3 は成功、C6/H2 は失敗） | S3 は C3 と同じ世代 |
| §4.16 / §4.17 | 独自のマウス報告を含む 10 種類の報告を送るキーボード、キーを押すたびに ErrorRollOver を大量に送るキーボードがある | 本家コアの汎用的な記述子解析を移植すれば対応しやすい |

検証されているのは「入力 2 台＋PC への BLE 出力 1 台」の 3 接続まで。作者の測定では、遅延は BLE で 15 ms 以下、USB で 2 ms 以下。

### 接続間隔の下限は未確定（2026-09-26 訂正）

会話の中で一度「ESP32 ではマウスの応答速度の上限（15 ms）はコードでは直せない」と説明したが、言い過ぎだった。

- 間隔を決めて要求を受けるか断るかは、Espressif が中身を公開していない BLE コントローラが行う。要求の出し方（ホスト側、NimBLE）は変えられる。
- 先行例は、PC とも BLE でつながった 3 接続の状態で、**つないだ後に**短くする要求だけを試した。作者自身が「断る基準は分からない。PC との接続を外して試せば分かる」と書いており、その実験はしていない。
- Orbit は PC へ USB で出すので PC との BLE 接続がなく、**接続時に最初から 7.5 ms を指定する方法**も試されていない。同じ S3 で、機器の側が求めた 7.5 ms の接続は維持されていた。
- 市販の BLE マウスも 7.5〜15 ms 程度で動くものが多く、15 ms でも Orbit の用途では足りる可能性が高い。
- XIAO（本家 BLE 版）は 7.5 ms を要求する設定だが、複数台接続時の実際の間隔は未測定。

→ 初代 M5Dial と BLE マウス 1 台で、接続時に 7.5 ms を指定した実験をすれば決着がつく（open-questions Q27）。

## bt-keyboard-remapper

- BTstack の Classic HID ホストでキーボードを受け、Classic の HID 機器か BLE の HID（`hids_device`）として PC へ出す。キーボード 1 台と PC 1 台。
- リマップは 256 個の変換表でキーコードを置き換える方式と、「修飾キーと組み合わせたときの動作」を入れ替える規則（`remap -c`）。設定はシリアルのコマンド。JSON を Go 製ツールで変換して読み込ませる。
- ESP32-S3 は Classic に非対応で、BTstack のライセンスは公開前提の Orbit と合わないため、流用しない。

## Cardputer KB

- PlatformIO（ボード指定 `m5stack-stamps3`）、NimBLE-Arduino 1.4、ESP32-BLE-Keyboard、ArduinoJson。Wi-Fi の Web 設定画面と OTA 更新（2 つの OTA 領域）を持つ。
- PSRAM のない ESP32-S3FN8 で BLE・Wi-Fi・Web 画面が同時に動く実例（BLE 接続は PC への 1 本だけ）。複数台の機器を受ける Orbit は、これよりメモリを使う（Q26）。
- M5Dial 側のファームを作るときの設定の見本になる。

## 追加調査：ESP32-S3 で「BLE で受けて USB で出す」実例（2026-09-26）

「S3 が親（セントラル）として 7.5 ms で通信した実測例」は見つからなかった。見つかった S3 の実例は次のとおり。

Espressif の資料：ESP32-S3 の同時接続は最大 9。複数接続では「台数を増やすほど間隔を長くする」「親として複数につなぐときは、各接続の間隔を同じ値か整数倍にそろえる」ことを推奨（具体的な数値表はない）。

## nRF52840 に BLE の実績が多い理由（2026-09-26 整理）

BLE は「①無線回路 ②コントローラ（無線の予定表係。メーカー製で中身は非公開）③ホスト（接続手順・ペアリング。Zephyr や NimBLE）④アプリ」の 4 層で動く。

- ①の仕様は ESP32-S3 の方が上（送信 +20 dBm / 受信 −97.5 dBm。nRF52840 は +8 dBm / −95 dBm）。ただし S3 は Wi-Fi と無線を共用する（Wi-Fi を使わなければ BLE が独占）。
- 差は②〜④と使われてきた量にある。nRF52840 はワイヤレスキーボードの定番で、ZMK の分割キーボードやドングルは nRF52840 が**機器を受ける側として 7.5 ms で通信するのが標準**。本家 HID Remapper の作者も BLE 版に nRF52840 を選び、ESP32（初代）は Bluetooth Classic 版の試作にだけ使っている。
- ESP32 の BLE は「スマホからつながれる側」の用途が中心で、キーボードやマウスを受ける側の部品（`esp_hidh`）には多数の不具合が記録されている。
- 結論：S3 には「1〜2 台を 15 ms で受ける」実績がある。「複数台を 7.5 ms で受ける」実績は見つからず、その実績があるのは nRF52840。
