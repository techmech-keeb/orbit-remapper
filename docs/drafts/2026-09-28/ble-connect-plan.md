# 先行事例を BLE の接続処理に反映する計画

[ble-connect-prior-art.md](ble-connect-prior-art.md) の調査を、`firmware/orbit/main/ble.c` に取り込む順番と、各段階の確かめ方・マージの時機を決める。**まだ何も実装していない。** 各段階の中身は、前の段階の実機の結果で変わりうる。

## 1. 方針

- **費用の小さい順に進める。** 設定を変えるだけの段階から始め、効かなかったら組み直しに進む。
- **1 段階 = 1 PR。** 段階ごとに `.bin` を渡し、ローカルのセッションが実機で確かめ、合格したらマージする。1 コミットごとにビルドを確かめる（M1 と同じ）。
- **本家コアは改造しない。** 変えるのは `ble.c`、`sdkconfig.defaults`、必要なら `storage.cc`。
- **新しい処理を足すたびに、不要になった古い処理を消す。** 避けるリストや見張りを積み増していくと、M1 の後半のように処理が絡み合う。

## 2. 段階

### 段階 0：この記録（PR [techmech-keeb/orbit-remapper#11](https://github.com/techmech-keeb/orbit-remapper/pull/11) に同梱）

調査と計画の文書だけ。コードは変えない。

### 段階 1：設定と小さな直し（1 PR）

実装済み：`205acae`（1a）、`f90e28c`（1b）、`f102c45`（1a で見つかった穴の直し）。`f90e28c` の試験は不合格（接続の試みが止まる不具合が 20 分で 8 回。原因は NimBLE が 0x3E の失敗を自分の再試行に任せて捨てること。[m1-results.md](../2026-09-27/m1-results.md) §3）。1b の結果：2 台とも `static` アドレスなので、段階 2 は許可リストでの接続（2-1）を選ぶ。`f102c45` の試験は合格（止まり 0 回、`0x3E` はすぐ回復）。新たに G''（5 秒ごとのつなぎ直しが解けない）→ `d2c4295` で直し、実機未確認。

| # | 変更 | 理由 |
| --- | --- | --- |
| 1a | NimBLE の接続失敗時の自動再試行を切る（`CONFIG_BT_NIMBLE_ENABLE_CONN_REATTEMPT=n`） | 切断イベントを Orbit に渡したうえで、NimBLE も裏で接続をやり直す。Orbit の接続とぶつかる（prior-art §4）。接続を始めるのは Orbit だけにする |
| 1b | ログに機器のアドレスの種類（公開、固定のランダム、変わるアドレス）を出す。アドレス自体は今までどおり下位 2 バイトだけ | 段階 2 の許可リストでの接続の前提を確かめる |
| 1c | esp-idf#18893 と #19057 の議論を読み、G' に当てはまる回避策があれば入れる | **読んだ結果（2026-09-28）：見送り。** #18893 は暗号化の直後から双方向の通信が全部止まり、約 16 秒で監視タイムアウト（0x08）になる。G' は暗号化後も接続は生きていて、探索の要求への返事だけが 30 秒来ない（ATT の時間切れ）。別の症状と見る。回避策も未提示。#19057 はアプリがデータ長の変更を暗号化より先に出した場合の話で、`ble.c` はデータ長を変えていない（暗号化は接続の直後に要求している）。コントローラが自動で変えているかは要確認 |

スキャン重複キャッシュ（問題 A）は、スキャンを始めるときにコントローラの重複除去を使わない設定にした `be58153` で対処済みなので、段階 1 では触らない。

**確かめ方**（ローカルのセッション、m1-handoff §0 に書く）：

1. 電源の入れ直し、機器のスリープからの復帰、機器の電源の入れ直しで、2 台が自動でつながるまでの時間。ログの `EVT` の時刻で測る。
2. G' の再現手順（Forget all devices → MD600 をリセット → ペアリング）で、使えない時間。
3. 10 分の連続使用（切断、`lost`、`LAT`）。
4. 2 台のアドレスの種類。

**合格**：1 と 2 が `eb9a5af` より悪くならず、3 で切断 0。4 が分かる。

### 段階 2：接続の組み立てを型に合わせる（1 PR、数コミット）

段階 1 の 4 の結果で、2-1 の方式を選ぶ。

| # | 変更 | 借りる先 | 消せる処理 |
| --- | --- | --- | --- |
| 2-1 | ボンド済みの機器の再接続を、許可リストへの 1 回の接続要求にする（`ble_gap_wl_set` → `ble_gap_connect` に接続先を空で渡す）。先に応答した機器がつながる。上限 15 秒で、切れたら出し直す。スキャンはペアリングのときだけ。**2 台のアドレスが変わる種類なら**、解決リストが使えるか確かめ、だめなら今のスキャンと照合の方式を残す | RMK、Linux、HOGP §5.2.2 | 自前の照合、スキャンの再開の時機合わせの大半 |
| 2-2 | 暗号化と探索の間は、スキャンも次の接続も始めない。探索は 1 台ずつ | nRF Desktop | — |
| 2-3 | 失敗した機器は、30 秒避ける代わりに、1 台あたりの試行回数（2 回）に上限を付ける。上限に達したら、次に機器が広告を出し直すまで（許可リストなら次の接続要求まで）待つ | nRF Desktop | 避けるリスト |
| 2-4 | 切断後、0.5 秒待ってから再接続に入る | RMK、本家 BLE 版 | — |
| 2-5 | スキャンの頻度を段階で変える。切断直後の 30 秒は今の 60 ms 間隔・30 ms 窓、その後は 1.28 秒間隔・11.25 ms 窓。入力が流れている間はスキャンを止め、最後の入力から 1 秒後に再開する | HOGP §5.2.3〜5.2.5、本家 BLE 版 | — |

2-5 には、つないでいる機器の 7.5 ms の通信にスキャンが割り込む時間を減らす効果も見込める（推測）。`LAT` と `lost` で確かめる。

見張り（接続が 15 秒止まったら取り消す、25 秒でホストをリセット、探索が 5 秒止まったら切る）は、段階 2 の後も残す。esp-nimble-cpp や RMK も、接続に自前の上限を持っている。

**確かめ方**：段階 1 の 1〜3 に加えて、次の 3 つ。

- 片方の機器の電源を切ったまま、もう片方を 10 分使う（スキャンの頻度を落とした効果）。
- ペアリングの新規と、Forget all devices からの組み直し。
- 暗号化に失敗する機器（もう一方の機器側でボンドを消した状態）が、スロットを占め続けないこと。

**合格**：段階 1 の合格条件に加えて、上の 3 つで問題がないこと。自動再接続の時間の目標値は、段階 1 の実測を見て利用者と決める。参考値は、Logi Bolt の受信機経由で 300 ms、Keychron で約 3 秒。

### 段階 3：ボンド済みの機器の探索を省く（1 PR）

1. まず `CONFIG_BT_NIMBLE_GATT_CACHING` を有効にし、MD600 と meteorite40 で再接続時に探索が省かれるかをログで確かめる。
2. 省かれない場合（機器が Database Hash を持たない等）は、Orbit 側で保存する。
   - 保存するもの：HID サービスの範囲、入力レポートのハンドルと Report Reference、Report Map。
   - 保存先：NVS。ボンドの記録に対応させる。
   - 再接続では、保存したハンドルに CCCD を書くだけにする。CCCD は規格上は保持されるが、Zephyr と同じく書き直す。
   - Service Changed の通知を受けたとき、ATT のエラーが出たとき、読み出しが失敗したときは、保存した情報を捨てて探索し直す。
   - Report Map は大きい（数百バイト）ので、NVS の容量と、設定の保存（Q34）との兼ね合いを測る。

**確かめ方**：再接続から入力できるまでの時間が縮むこと。G' の再現手順で使えない時間。機器のファームウェア更新などで構成が変わった場合を模して、保存情報を壊した状態から自動で復旧すること。

### 段階 4：Zephyr 案の評価（必要な場合だけ）

段階 1〜2 で安定しなければ、本家 BLE 版を Zephyr ごと S3 に載せる案を評価する。Zephyr の S3 対応（Bluetooth と USB デバイス）の調査から始める。今の ESP-IDF 構成を捨てることになるので、進めるかは利用者が決める。

### 見送るもの

- ESP-IDF の `esp_hidh` への乗り換え（prior-art §3.7）。
- スキャン中の接続（`BT_NIMBLE_HOST_ALLOW_CONNECT_WITH_SCAN`。C3 で落ちる報告）。

## 3. マージの時機

| PR | 中身 | マージの時機 |
| --- | --- | --- |
| [techmech-keeb/orbit-remapper#11](https://github.com/techmech-keeb/orbit-remapper/pull/11) | 問題 G の直し（実機で確認済み）、G' の見張り `eb9a5af`（未確認）、この調査と計画 | **今マージしてよい。** G の直しは `a195bc8` の試験で効いた。`eb9a5af` は、5 秒止まった探索の接続を切るだけで、その接続はもともと 30 秒使えなかった。悪化する経路は小さく、段階 1 の版でまとめて確かめられる |
| 段階 1 の PR | §2 段階 1 | ローカルのセッションの試験で合格したら |
| 段階 2 の PR | §2 段階 2 | 同上 |
| 段階 3 の PR | §2 段階 3 | 同上 |

- マージは利用者が行う。クラウドのセッションはマージしない。
- マージの後、クラウドのセッションは同じ名前のブランチ `claude/laughing-volta-r6lpn4` を最新の `main` から切り直し、次の段階の PR を新しく作る。マージ済みの PR には追加しない。
- 試験の報告だけの PR（ローカルのセッションが作る、PR #10 のようなもの）は、中身を確かめたらいつでもマージしてよい。
