# M1 の報告：版 `09b3075`（`orbit-m1-09b3075-ble.bin`、2026-09-28）

利用者の PC（Windows 11、PC 本体のポート）と初代 M5Dial で、m1-handoff.md §0（`8de5510` 版）の 1〜3 を行った。`.bin` の SHA-256 は一致。書き込みモードへは PC 側から 1200 bps で入れた。ログは COM11（115200 bps、DTR あり）。`M1` の行は全部ファイルに残した（`m1-09b3075-M1-lines.log` 6,827 行。利用者の PC に保存、リポジトリには入れていない）。機器：MD600（キーボード）、meteorite40（トラックボール付きキーボード）。

## 新しく分かった問題（直してほしい順）

### 1. つなぎに行く試みに時間切れがなく、相手が消えると本体が探せなくなる（2 回再現）

- **00:38:29**：利用者が meteorite40 を再起動 → 本体が `connecting`（00:38:30）→ **接続も失敗も出ないまま約 2 分**。その間 `scan=0`。Pair new device（00:40:21）を押しても `scan start (pairing)` が出ない。RST（00:40:44）で復旧。
- **00:48:53**：meteorite40 の電源を切った瞬間に本体が `connecting` → 同じく止まる。`scan=0`、Pair new device（00:49:00）が効かない。RST（00:50:09）で復旧。
- 一方、今日の A10（電源の入れ直し）では問題なかった。**相手が広告を出した直後に消えるタイミング**で起きる。
- `ble_gap_connect()` に時間切れ（例：2〜5 秒）を付け、失敗したら探し直す。これがないと、実運用で本体を RST するしかなくなる。

### 2. 暗号化に失敗して切ったあと、同じ機器にすぐつなぎ直して失敗をくり返す

- Forget all devices（00:44:06）の後、古い鍵の 2 台に対して「つなぐ → `encryption failed` → 切る（`hci=0x05`）→ つなぐ」が続いた。**約 2 分 10 秒で 280 回**（MD600 40 回：約 65 ms 周期、meteorite40 240 回：約 0.4 秒周期）。ログは 1 秒に約 170 行。
- くり返している間、他の機器（ペアリング待ちにした MD600）が見つからなかった（Pair new device を押しても meteorite40 だけを何度もつかむ）。
- 失敗した相手を一定時間（数十秒）避ける、または連続で N 回失敗したら避ける、が必要。

### 3. 暗号化を「始められなかった」接続は切られない

- くり返しの中で 1 回、`security start failed rc=0x6, discovering anyway`（00:44:11、MD600）。この接続は切られず、`enc=0 subs=0` のまま枠を占めた（MD600 のリセットで相手から切れるまで）。
- 「暗号化に失敗したら切る」の直しが、「始められなかった」経路を含んでいない。`rc=0x6` は、直前の接続の後始末が終わる前に次の接続を始めたため（問題 2 の副作用）と見ている（推測）。

### 4. 確かめてほしいこと：ペアリング待ちでないのに再ペアリングを受け入れていないか（推測）

- 00:42:44：利用者が meteorite40 で BT クリアの操作 → 切断 → 本体が `scan start (bonded devices only)` でつなぎ直し → **`encryption on`**（0.37 秒後）。期待した `encryption failed` にならなかった。
- BT クリアが効いていなかった可能性が高い（00:53:27 に同じ操作をやり直したら、Pair new device の後に新しい鍵でつながった）。ただし、**機器が「鍵がない」と言ってきたときに、ペアリング待ちでなくても本体がペアリングを受け入れる**作りになっていないかは、ソースで確かめてほしい。受け入れるなら、登録済みのアドレスを名乗る機器が再ペアリングできてしまう。
