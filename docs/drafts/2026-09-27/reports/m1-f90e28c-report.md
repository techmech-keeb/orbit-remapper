**止まる不具合がこの版で大きく悪化していたため、手順 3 の途中で打ち切った**（利用者の判断）。手順 3（G'）の本番と 4（10 分）は行っていない。

## 止まる不具合の詳細（最重要）

### 起きた 8 回（すべて meteorite40 `e4:f9`、`adv_type=0`、`addr_kind=static`）

| 21:27:56（t=3.62） | RST 4 回目 | 同上（t=30.3） |
| 21:29:18（t=3.64） | RST 5 回目 | 同上（t=30.0） |
| 21:32:57 | Forget all devices で本体が meteorite40 を切った 0.3 秒後 | リセット → 直後の接続がまた止まる |
| 21:33:23 | BLE ホストのリセットの 0.3 秒後 | 同上 |

- この版の meteorite40 への接続の試み 25 回のうち、**8 回（32%）が止まった**。MD600 への試みは 10 回で、止まったのは 0 回。
- 止まったときは、`connecting` のあと**成功（`connected`）も失敗（切断や `0x3E`）も一切報告されない**。15 秒の取り消しは毎回 `rc=0x2` で失敗する。
- 止まったのは、①M5Dial の起動直後の最初の接続、②本体が meteorite40 を切った直後・BLE ホストのリセット直後・30 秒の避ける期間の明け、の場面。どれも「**meteorite40 が広告を出し始めた、またはつなぎ直しの準備中**」のタイミングと見ている（推測）。
- Forget all devices の後は、本体が meteorite40 をつかむ → 止まる → 25 秒でリセット → すぐまた meteorite40 をつかむ → 止まる、を約 7 分くり返し、**その間 MD600 を一度も見つけられなかった**（探索している時間が 0.1〜0.3 秒しかない）。利用者が RST して、MD600 だけが先に見つかる形で抜けた。

### 見立て（推測）

- 前の版では、同じ場面でも止まらなかった（`8061951` で 1 回、`0a0cfcf` で 2 回、どれも数十分に 1 回）。**この版の変更「NimBLE 自身の接続の再試行を止めた」で悪化した**可能性が高い。
- 接続の確立に失敗する（`0x3E` 相当）ことは前からあったが、NimBLE が裏でやり直して救っていた。やり直しを止めたとき、**失敗の知らせ（`BLE_GAP_EVENT_CONNECT` の status≠0、または `DISCONNECT`）が ble.c に届かない経路**ができたのではないか。ble.c から見ると、接続を始めたまま何も返ってこない＝止まる、になる。
- 確かめてほしい：接続の再試行を止める変更で、`BLE_ERR_CONN_ESTABLISHMENT`（0x3E）のときに NimBLE がアプリに何を通知するか。通知されないなら、ble.c が自分で「`connecting` から N 秒（例：1〜2 秒）で `connected` が来なければ取り消してやり直す」必要がある。**この版は `eb9a5af` に戻すか、失敗の通知を確実に受け取る直しを入れてから再試験したい。**

## そのほかに分かったこと

### 古い MD600 のペアリング情報が残る

- MD600 はリセットするたびにアドレスが変わる。21:40 に RST 後にペアリングした MD600（`c7:6e`、ポート 1）は、そのあと利用者が MD600 をリセットしたため使われなくなったが、**本体のペアリング情報に残ったまま**。次にペアリングした MD600（`0b:2a`）はポート 2 になった。
- ペアリング情報の上限（ESP-IDF の既定 3 件）に達すると、新しい機器をペアリングできなくなる可能性がある。M2 の機器台帳（決定 I4）で、「使われなくなった古い情報を消す」操作が要る。

### MD600 のリセット直後の動きが前と違った

- 前の版では、MD600 はリセット直後のペアリングで**探索の途中**で自分から切っていた（G' の原因の場面）。今回は 2 回とも**探索まで完走**し、1 回目（`c7:6e`）はその 6 秒後に自分から切った（`hci=0x13`）。2 回目（`0b:2a`）は切らなかった。MD600 側の事情か、本体側の変更（GATT の見張りなど）の影響かは分からない。
