# 実装設計：D 案（M5Dial 単体）のファームをどう分けて作るか

Q31 の結果を受けて D 案（requirements H5）に切り替えた後、ファームをどの順番で、どう分けて作るかの設計。本家 HID Remapper のソース（master、2026-09-27 に確認。コミット `51ab8b3`。hid-remapper-capabilities.md が参照している版と同じ）と、[requirements.md](../2026-09-26/requirements.md)（F1〜F5、U1〜U4）、[development.md](../2026-09-26/development.md)、[prior-art.md](../2026-09-26/prior-art.md)、[q31-results.md](q31-results.md) に基づく。**実装はまだ始めていない。**

## 1. 結論

- **3 つの区切りで作る**：M1「本家をそのまま動かす」→ M2「Orbit の芯（機器ごとの機能と新しい部品）」→ M3「画面」。
- 本家はすでに「コア」と「マイコン依存部」に分かれていて、BLE 版のマイコン依存部は `main.cc` 1 ファイル（約 1,000 行）だけ。**M1 はこのファイルの ESP-IDF 版を書くこと**で、範囲がはっきりしている。
- 「追加機能」には**本家コアを改造するもの**（機器ごとのレイヤーなど）と**コアに触らない新しい部品**（設定セット、ペアリング管理など）の 2 種類がある。前者は差分を最小にしたパッチとして持ち、後者は Orbit 独自の層に置く。
- 画面に出す**情報（状態の写し）と操作（命令）の型を M2 で決め**、M3 の画面はそれだけを使う。M1・M2 では同じ情報をシリアルの文字で出して試験する。
- 設計上の 6 つの決定は §5。ユーザーの決定（2026-09-27）：**4 は C（住所に固定＋手動での付け替えを最初から）、それ以外は推奨案のとおり。画面はアニメーションより情報の見やすさを優先する。**

## 2. 本家の構造（事実）

| 部分 | ファイル | 行数 | 備考 |
| --- | --- | --- | --- |
| コア | `firmware/src/remapper.cc`、`config.cc`、`descriptor_parser.cc`、`our_descriptor.cc`、`quirks.cc`、`crc.cc`、`globals.cc`、`interval_override.cc`、`ps_auth.cc` | 約 6,500 | USB 版と BLE 版が**同じファイルを共有**（`firmware-bluetooth/CMakeLists.txt` で参照） |
| BLE 版のマイコン依存部 | `firmware-bluetooth/src/main.cc` | 1,005 | Zephyr（nRF52840）。コアが要求する関数は `platform.h` の 12 個と `queue_out_report` など数個 |
| USB 版の PC 側 USB | `firmware/src/tinyusb_stuff.cc` | 238 | boot protocol（BIOS 対応、F4-2）とリモートウェイクアップ（F4-3）は**USB 版にしかない** |

BLE 版の主ループ（`main.cc` の `main()`）：受信した報告をキューから取り出して `handle_received_report()` → 1 ms ごとに `process_mapping()` → `send_report()` → `send_monitor_report()`。切断・記述子・PC からの設定もキュー経由。**コアは 1 つの処理からしか呼ばれない前提**で書かれている。

コアの状態はグローバル変数で、本体全体に 1 つずつ：`layer_state_mask`（レイヤー）、`input_state`、`sticky_state`、`tap_hold_state`、`accumulated`（`remapper.cc` 61〜92 行）。**機器ごとのレイヤー（F2-2）と切断時の解除（F2-5）は、ここを変える必要がある。**

設定の保存形式は版 3〜13 が存在し（`config.cc` の `load_config_v*`）、PC の設定ツールは USB の 2 つ目の HID 窓口（本家 BLE 版の `HID_1`）で本体と話す。

## 3. 層の分け方

依存は上から下へだけ。下の層は上の層を知らない。

```
表示層     : (a) シリアル文字表示（M1〜）   (b) LVGL の画面（M3）
アプリ層   : 機器台帳（住所 → 安定した番号 → 本家のポート番号）/ 設定セット /
             ペアリング管理 / 機器ごとのレイヤー / LED の送り返し（F5）/
             状態の写しを作る / 主ループ
コア層     : 本家コア（取り込み＋最小のパッチ）。境界は remapper.h と platform.h
基盤層     : NimBLE の HOGP 受信 / TinyUSB の機器側 / 保存（NVS）/ 1 ms の刻み /
             M5Dial の画面・タッチ・ダイヤル・ボタン・電源保持
```

| 層 | 元にするもの |
| --- | --- |
| NimBLE の HOGP 受信 | **Q31 の `experiments/q31-s3-two-ble/main/ble_central.c` が種**。接続時に 7.5 ms を指定、GATT サーバー有効、自分から暗号化、`esp_hidh` を使わない（q31-results.md §3・§5） |
| TinyUSB の機器側 | 本家 **USB 版**の `tinyusb_stuff.cc`（F4-2、F4-3 のため） |
| 主ループ | 本家 BLE 版 `main.cc` の写し |
| 画面の部品 | Q31 の `display.c` は試験用。製品は LVGL（`esp_lvgl_port`）に置き換える |

**状態の写し**（アプリ層 → 表示層）：接続中の機器（安定した番号、名前、実際の接続間隔、切断・再接続中）、機器ごとの現在のレイヤー、ペアリング待ちかどうか、今の設定セット、直近のできごと。
**命令**（表示層 → アプリ層）：レイヤー切替（F3-2）、ペアリング開始・1 台削除（F3-3）、設定セット切替（F3-4）、割り当ての入れ替え・削除（F3-5）、機器の付け替え（§5 の決定 4）。

## 4. 区切り（マイルストーン）

| 区切り | 中身 | 「できた」の条件 |
| --- | --- | --- |
| M1 本家そのまま | 基盤層と主ループ。本家コアは無改造。表示はシリアル文字だけ | 本家 XIAO 版と同じ動き（2 台・7.5 ms、PC の設定ツールで設定と保存ができる、BIOS で使える、スリープ解除）。**空きメモリの最小値と、受信から USB 送信までの遅れを測る**（決定 3・6） |
| M2 Orbit の芯 | コアへのパッチ（F2-2、F2-5、F1-4）と、アプリ層の部品（機器台帳、設定セット、ペアリング管理、F5）。状態の写しと命令の型を確定。操作は本体のボタン・ダイヤルとシリアル | F1〜F5 を**画面なしで**すべて試験できる |
| M3 画面 | LVGL で F3-1〜F3-5 | 画面を作り直しても、コア層とアプリ層に手が入らない |
| 常時 | 本家の更新の取り込み（専用 PR）、実機の試験表、メモリ使用量の記録 | ― |

M1 を「本家と同じ」で終える理由：**本家との差分ゼロの基準点**ができ、問題が出たとき「移植のせいか、改造のせいか」を切り分けられる。

## 5. 設計上の決定（2026-09-27）

各項目は「それは何か」「選択肢と結果」「決定」の順。決定はユーザーが 2026-09-27 に選んだもの。

### 決定 1：本家コードの取り込み方と改造の管理

**何か**：本家コア（約 6,500 行）を Orbit のリポジトリでどう持つか。本家は更新が続いている（2026-08-29 に試験版）。development.md により、public のフォークには独自変更を入れない。

| 選択肢 | 良い点 | 困る点 |
| --- | --- | --- |
| A. コピー | 簡単 | 本家の更新の取り込みが手作業。改造箇所が分からなくなる |
| B. submodule（参照だけ） | 本家の版がはっきりする | 参照先が public なので改造を書けない。clone 時に中身が空になりがち |
| C. subtree（履歴に取り込む） | 改造をその場で書ける。clone すれば全部そろう。本家の更新をマージで取り込める | 履歴に本家のコミットが混ざる |

**決定：C（subtree）。改造は最小にし、改造箇所に `// ORBIT:` の印を付ける。** パッチファイル方式は管理が難しいので採らない。Orbit は private で、公開時は `main` の履歴だけを新リポジトリへ push する方針（development.md）なので、履歴に本家（MIT）が混ざっても問題ない。

### 決定 2：タスクの分け方と 1 ms の刻み

**何か**：ESP32-S3 は CPU が 2 つ。BLE 受信（NimBLE）、コアの主ループ、USB（TinyUSB）、画面（LVGL）をどう並べ、どうデータを渡すか。コアは 1 つの処理からしか呼ばれない前提（§2）なので、複数の処理から同時に呼ぶと再現しにくい不具合になる。本家コアは 1 ms ごとに `process_mapping()` を呼ばれる前提で、タップ／ホールドやマクロの時間をこの刻みで数える。

| 項目 | 選択肢 | 決定 |
| --- | --- | --- |
| コアを呼ぶ処理 | 1 つに絞る／受信処理が直接呼ぶ | **1 つに絞る**。BLE 受信はキューに入れるだけ（本家 BLE 版と同じ） |
| CPU の割り当て | BLE を CPU0、主ループを CPU1／成り行き | **BLE を CPU0、主ループを CPU1**（Q31 と同じ）。無線は 7.5 ms ごとの通信を落とすと切れるため、他の処理と分ける |
| 1 ms の刻み | USB の SOF（PC の合図。PC が止まると止まる）／内蔵タイマー | **`esp_timer`**（本家 BLE 版と同じ。常に動く） |
| 画面 | 低い優先度の別タスク／高い優先度 | **低い優先度の別タスク**。入力の処理が常に先 |

**結果**：入力の遅れが安定し、再現しにくい不具合を避けられる。速さの差はほとんど出ない。**後から変えにくい**ので最初に固める。

### 決定 3：メモリ（RAM）の予算

**何か**：M5Dial は RAM 512 KB、PSRAM なし。ESP-IDF、NimBLE、TinyUSB、本家コア（設定の大きさで増える）、LVGL の描画バッファを収める。画面は 240×240×2 バイト＝**1 画面約 115 KB**。

| 画面バッファ | メモリ | 見え方 |
| --- | --- | --- |
| 全画面 ×2 | 約 230 KB | 最もなめらか。**入らない** |
| 全画面 ×1 | 約 115 KB | 残りが厳しい |
| 部分（240×40 ×2） | 約 38 KB | 帯状に描く。静止した情報表示なら差は分からない。大きなアニメーションはちらつくことがある |

**決定：部分バッファ 40〜60 KB を M1 の時点で確保だけしておき、M1 の終わりに空きメモリの最小値を測る。** ユーザー決定：**画面はアニメーションより情報の見やすさを優先する。** 空きが 50 KB を切るなら、設定の上限を下げるかバッファを縮める（数値は目安。実測で決める。Q26）。

### 決定 4：機器の安定した番号

**何か**：本家は設定の中で機器を 1〜15 の「ポート番号」で区別する（0 は全機器）。BLE には差し込み口がないため、本家 BLE 版は**ペアリングした順**で番号を振る。Orbit の機器ごとの機能（F2-2、F2-5、F3-1、F3-3）は、番号が安定していないと「どの機器の話か」を間違える。Q31 でも、起動のたびに D0/D1 が入れ替わった。

| 選択肢 | 結果 |
| --- | --- |
| A. ペアリング順（本家のまま） | 1 台削除すると番号がずれ、設定が別の機器に効く。**機器ごとの機能は事実上作れない** |
| B. 住所に固定 | 機器の Bluetooth の識別アドレス（ペアリングで交換する住所）を鍵に、番号を永続的に割り当てる。**機器側でペアリングを消してやり直すと住所が変わることがある**（Q31 で MD600 が `c9:c6` → `a9:2f` → `ae:4f` と変わった）。その場合は「新しい機器」として現れ、設定をやり直す |
| C. B ＋ 手動での付け替え | 画面で「この新しい機器は、以前の 3 番と同じ扱いにする」と指定できる。UI が 1 つ増える |

**決定（ユーザー）：C を最初から作る。** 番号は本家の 1〜15 の枠をそのまま使い、PC の設定ツールからは「ポート番号」として見える（F1-4）。機器台帳（住所、番号、名前）はアプリ層が NVS に持つ。

### 決定 5：設定セットの保存形式と PC の設定ツール

**何か**：本家は設定を 1 つしか持てない。Orbit は複数（F3-4）。本家の形式はすでに版 13 まで変わっている（§2）。

| 項目 | 選択肢 | 決定 |
| --- | --- | --- |
| 保存の形 | 本家形式の塊 × N ＋ Orbit のヘッダー／Orbit 独自形式 | **本家形式 × N**。本家の PC ツールがそのまま使え、本家の版が上がっても本家の読み込み処理が面倒を見る |
| PC ツールがどのセットを編集するか | 本体で選んだセットを「その 1 つ」として見る／PC ツールにセット選択を追加 | **本体で選んでから PC で編集**。PC ツールは無改造 |
| 保存先 | NVS（名前付きの保存箱）／専用パーティション | **NVS**。ペアリング情報も NimBLE が NVS に置くので揃う |

**結果**：PC 側の作業は本家とまったく同じ。Orbit で足すのは本体側の切替だけ。保存できる数は M2 で実測して決める（8 MB のフラッシュなら十数〜数十セットの見込み。推測）。

### 決定 6：入力の遅れ（レイテンシ）の目標

**何か**：キーを押してから PC に届くまでの時間。Q31 で 7.5 ms を勝ち取っても、中の処理が遅ければ意味がない。目標がないと M1 の良し悪しを言えない。

内訳の目安（推測。実測で埋める）：機器が送るまで 0〜7.5 ms（機器次第）、M5Dial の受信 → 主ループ 1 ms 未満、1 ms の刻み待ち 0〜1 ms、USB で PC へ 0〜1 ms。

| 目標 | 結果 |
| --- | --- |
| 本家 XIAO 版と同等 | 比較で判断。XIAO 版も未測定 |
| Orbit の中で 3 ms 以内 | 受信から USB 送信までを本体のログで測る。道具が不要。PC や機器の影響を受けずに Orbit の出来だけを評価できる |
| PC で測って合計 10 ms 以内 | 体感に近いが、高速なロガーなどの道具が要る |

**決定：Orbit の中で 3 ms 以内を M1 の合格条件にし、本体のログで測る**（Q31 の `DEV` 行の応用）。端から端の測定は道具がそろってから任意で。

## 6. 避けること

- コアを ESP-IDF 風に書き直す。本家の更新を取り込めなくなる。
- 表示層がコアの内部（`layer_state_mask` など）を直接読む。M3 が M2 に食い込む。
- 画面の描画とコアの主ループを同じタスクで回す。
- `esp_hidh` を使う（prior-art.md の不具合表。Q31 で回避済み）。

## 7. 未確認のこと

- 各部品のメモリ使用量（決定 3 の数値はすべて目安）。
- 遅れの内訳（決定 6）。
- 本家形式の設定 1 つあたりの大きさと、保存できるセット数（決定 5）。
- M5Dial の画面・タッチ・ダイヤルと BLE・USB を同時に動かしたときの影響（Q25）。
- PC の設定ツールが、Orbit の「ポート番号」（決定 4）をそのまま扱えるか（本家 BLE 版のポート番号の扱いに合わせる見込み）。
