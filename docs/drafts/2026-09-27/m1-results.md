# M1 の結果：本家 HID Remapper を M5Dial で動かす

依頼書 [m1-brief.md](m1-brief.md) §5 の合格条件を、初代 M5Dial と利用者の PC（Windows 11、PC 本体の USB ポート）で確かめた記録。機器は Mistel MD600 Alpha（キーボード）と meteorite40（トラックボール付きキーボード）。実装は `firmware/orbit/`（PR [techmech-keeb/orbit-remapper#9](https://github.com/techmech-keeb/orbit-remapper/pull/9)）。事実（ログで見た値）と推測を分けて書く。ログの全文は利用者の PC にだけある。

## 1. 結論

- **本家の BLE 版と同じことが M5Dial 1 台でできた。** 2 台を 7.50 ms・latency 0 で受け、本家コア（無改造）でリマップし、USB HID として PC へ出し、本家の Web 設定ツールで設定・保存できる。
- A1〜A4、A7〜A10 は合格。A8 は 2 台同時で最大 1.85 ms。A5（BIOS）と A6（PC のスリープ解除）は未確認。
- 空きメモリの最小値は **74.5 KB**（LVGL 用 48 KB を確保した状態、設定の保存時）。ふだんは 92〜98 KB。
- 見つかった問題と直し：USB の送信口は 5 本まで（0x84 以下）、製品名に `Bluetooth` が要る、暗号化に失敗した接続は切る、`LAT` の基準の取り方。未解決：USB ハブ経由で書き込みモードに入れないことがある。

## 3. 考察

- **`LAT` の大きな値は測り方によるもの**（`09b3075` で裏付け）。`6254d16` は「まだ送信に反映されていない最も古い受信」を基準にしていたので、出力を変えない報告（本家コアの中で合算される小さな動きなど）を基準にしたまま、次に出力が変わるまでの時間を測っていた。最も新しい受信を基準にし、20 ms 以上たった送信は「無関係」として数える版では、2 台同時でも最大 1.85 ms。
- **`0a0cfcf` の試験（事実）**：接続の試みが止まる不具合が自然に再現し、25 秒で BLE ホストをリセットして **RST なしで復旧**した。30 秒避ける・再ペアリングを断る、も動いた。新たに：A. リセット後や 30 秒の待ちが明けた後、ペアリング済みの機器が Pair new device を押すまで見つからない（1 時間以上）。B. 別の機器のペアリング中に正しい鍵の機器が `security start failed rc=0x6` で避けられる（2 回）。C. 鍵を消して黙っている機器が 30 秒枠を占める。D. ホストのリセットで正常な接続も切れる。E. 途中までの Report Map をコアに渡した。F. `cancel` の行が毎秒出る。
- **原因と直し（`8061951`、未確認）**：A は探索の重複フィルタ（`filter_duplicates=1`）。コントローラーは 1 回の探索で同じアドレスを 1 度しか報告しないため、避けている間に報告された機器は探索を始め直すまで報告されない → フィルタを外した。B は NimBLE がペアリング／暗号化の処理を同時に 1 つしか持てないため（`BLE_SM_MAX_PROCS=1`）→ 切らずに毎秒再試行。C は 5 秒で切って避ける。E・F は直した。D はそのまま（A が直れば自動でつながり直す見込み）。
- **`09b3075` で見つかった接続まわりの問題（事実）と直し（`0a0cfcf`、`8061951` の試験で確認済み）**：①機器が広告の直後に消えると、接続の試みが完了せず探索が止まった（2 回、RST で復旧）。NimBLE は取り消し後の完了イベントを待ち続ける既知の穴があるため、15 秒で取り消し、25 秒で BLE ホストをリセットする。②暗号化に失敗した機器が約 65 ms〜0.4 秒周期で再接続をくり返し（2 分で 280 回）、ほかの機器を探せなかった → 30 秒避ける。③`security start failed rc=0x6` の接続が切られずに枠を占めた → 切る。④ペアリング済みのアドレスを名乗る機器の再ペアリングを無条件に受け入れていた → ペアリング待ちのときだけ受け入れる。
- **暗号化に失敗した接続を持ったままにすると枠が埋まる**（事実）。機器側に古い鍵が残っていると `encryption failed`（`0x503`／`0x505`）のまま接続が残る。次の版では本体から切る。機器側でペアリングを消してもらう必要は変わらない。
- **本家のポート番号はペアリングの順で入れ替わる**（事実。1 回目は MD600＝1、meteorite40＝2。Forget all devices 後は逆）。本家どおりで、M2 の決定 4（住所に固定＋手動での付け替え）で直す。
- **meteorite40 は再ペアリング後に latency 30 を求めてきた**（事実。`itvl=6-12 lat=30`）。7.50 ms・latency 30 で受けた。それまでの接続では要求は来なかった。latency は機器が省電力のために間引いてよい回数で、入力があるときは即座に送れるので遅れには効かない見込み（推測）。本家 BLE 版も機器の latency を受け入れる。影響は A8 の測り直しで見る。
- **書き込みでペアリング情報と設定が消えなくなった**（事実。NVS をアプリの後ろ `0x400000` に移した効果。Q31 では毎回消えた）。

## 4. 途中で分かったこと（次の人向け）

| 事実 | 対応 |
| --- | --- |
| ESP32-S3 の USB コントローラーは送信用の FIFO が IN endpoint 0〜4 の 5 本だけ（TinyUSB `dwc2_esp32.h`）。0x85 を使うと 1 バイトも出ない | HID 2 つと CDC で 0x81〜0x84。これ以上 IN endpoint は足せない |
| 本家の設定ツールは USB の製品名に `Bluetooth` が入っていないと Pair new device / Forget all devices を出さない（`config-tool-web/code.js`） | 製品名を `HID Remapper Bluetooth XXXX` に |
| ESP-IDF の再起動は USB シリアルをリセットしない。再起動前に USB シリアルの状態をいじる直し（`db94be3`）は、書き込みモードを PC から見えなくした。ボタン＋RST・1200 bps・電源の入れ直しでも復旧せず、**M5StampS3 の G0 を押しながら電源を入れる**（背面を開ける）でだけ復旧した | 取り消した。USB シリアルをいじる直しは G0 に手が届く状態で試す |
| `esp_tinyusb` 2.x は TinyUSB を必ず自分のタスクで回す | `espressif/tinyusb` を直接使い、主ループで回す（決定 I2） |
| 本家 BLE 版の 1 ms の刻みは USB の SOF（`status_cb`）。設計書の決定 2 の「`esp_timer`（本家 BLE 版と同じ）」の括弧内は事実と違う | M1 は決定どおり `esp_timer`。設計書は要修正 |
| 本家 BLE 版は報告の先頭に報告 ID を常に付けてコアに渡すが、報告 ID を使わない機器では 1 バイトずれる | `external_report_id` で渡す |
| 機器側でペアリングを消してやり直すと、MD600 はアドレスが変わる（`1f:64` → `26:27` → `5a:1d`） | M2 の決定 4 の「手動での付け替え」の根拠 |

## 5. 未確認のこと

- A5（BIOS）、A6（PC のスリープ解除。TinyUSB の ESP32-S3 版でリモートウェイクアップが動くか）。
- A8 の測り直し（`LAT` の基準を直した版）。latency 30 の影響も同時に見る。
- A7 を「2 台を動かし続けたまま 10 分」で厳密にやり直すか（利用者の判断）。
- USB ハブ経由で書き込みモードに入れない原因。
- 空きメモリ：設定の保存時に約 18 KB 下がる内訳（本家 `persist_config()` の一時バッファと NVS の書き込みと見ている。推測）。
