# M1 の結果：本家 HID Remapper を M5Dial で動かす

依頼書 [m1-brief.md](m1-brief.md) §5 の合格条件を、初代 M5Dial と利用者の PC（Windows 11）で確かめた記録。**つなぎ方の訂正（2026-09-29、利用者）**：9 月 28 日以降の試験（`8061951` 以降）はすべて USB ハブ（Genesys GL850、VID 05E3 / PID 0608）経由だった。9 月 27 日の `3662016`・`728105c` は報告どおり PC 本体のポートと、ハブ経由の両方を試した。9 月 27 日夜の `1e37eea`・`86a2d16`・`6254d16` はどちらだったか分からない。機器は Mistel MD600 Alpha（キーボード）と meteorite40（トラックボール付きキーボード）。実装は `firmware/orbit/`（PR [techmech-keeb/orbit-remapper#9](https://github.com/techmech-keeb/orbit-remapper/pull/9)）。事実（ログで見た値）と推測を分けて書く。ログの全文は利用者の PC にだけある。

## 1. 結論

- **本家の BLE 版と同じことが M5Dial 1 台でできた。** 2 台を 7.50 ms・latency 0 で受け、本家コア（無改造）でリマップし、USB HID として PC へ出し、本家の Web 設定ツールで設定・保存できる。
- A1〜A4、A6〜A10 は合格。A8 は 2 台同時で最大 1.85 ms。A5（BIOS）は未確認（先送り）。
- 空きメモリの最小値は **74.5 KB**（LVGL 用 48 KB を確保した状態、設定の保存時）。ふだんは 92〜98 KB。
- 見つかった問題と直し：USB の送信口は 5 本まで（0x84 以下）、製品名に `Bluetooth` が要る、暗号化に失敗した接続は切る、`LAT` の基準の取り方。USB ハブ経由でボタン＋RST が失敗した件（`3662016`）は、`1fd6c6a` ではハブ経由でも起きなかった（再現せず）。

## 3. 考察

- **`LAT` の大きな値は測り方によるもの**（`09b3075` で裏付け）。`6254d16` は「まだ送信に反映されていない最も古い受信」を基準にしていたので、出力を変えない報告（本家コアの中で合算される小さな動きなど）を基準にしたまま、次に出力が変わるまでの時間を測っていた。最も新しい受信を基準にし、20 ms 以上たった送信は「無関係」として数える版では、2 台同時でも最大 1.85 ms。
- **`8061951` の試験（事実）**：問題 A は解消（30 秒明けに Pair new device なしで見つかる、電源の入れ直しで自動接続）。接続の試みが止まる不具合は 3 回目の自然再現で、**止まってから約 31 秒で 2 台とも自動でつながり直した**（利用者の操作なし）。E・F も解消。新たに：G. 機器が探索の途中で切ってすぐつなぎ直すと、次の接続が `subscribed 0` のまま 30 秒使えない（2 回）。H. meteorite40 が暗号化の途中で 4 秒応答しない（機器の再起動で直った。前回の BT クリアのくり返しで鍵が食い違ったと見ている）。
- **`a195bc8` の試験（事実）**：問題 B（2 台同時の暗号化）は起動直後に自然に発生し、`retrying` → `security started` → 暗号化成功。正しい鍵の機器は切られなかった。G の「古い結果の紛れ込み」は消え、保険（登録ゼロなら切ってやり直す）も働いた（つなぎ直しで 0.5 秒で登録）。ただし **G'**：つなぎ直した接続の最初のサービス探索が 30 秒返事を待たされる（ATT の時間切れ `0xd`）のは変わらず、使えない時間は 30 秒のまま。2 台で 1 分の使用：切断 0、`LAT` 最大 1.82 ms。
- **`f90e28c` の試験（事実、段階 1 の版、途中で打ち切り）**：NimBLE の接続の再試行を止めたところ、接続の試みが止まる不具合が**約 20 分で 8 回**に増えた（すべて meteorite40、機器が広告を出し始めた直後）。止まったときは `connecting` の後に成功も失敗も報告されず、15 秒の取り消しは `rc=0x2`（「接続中ではない」）で失敗し、25 秒でホストをリセットして復旧。Forget all devices の後は「つかむ → 止まる → リセット」を 7 分くり返し、MD600 を探せなかった。機器の電源の入れ直しは 0.6〜0.7 秒でつながり直した。**2 台のアドレスの種類は `static`**（MD600 はリセットで値は変わるが種類は変わらない。rpa は一度も出ていない）。G' の場面は起きなかった（MD600 がリセット直後のペアリングで探索まで完走した）。
- **止まる不具合の原因と直し（`f102c45`、未確認）**：NimBLE は接続の完了の後、相手の機能と版を読んでからアプリに `CONNECT` を渡す。その間に接続が切れる（0x3E、相手が最初のパケットに答えない）と、`ble_gap_rx_rd_rem_sup_feat_complete()` は「自分の再試行が続く」と見なして読み取りの失敗を捨てる。再試行を止めた版では何も続かず、アプリが知らない接続番号の `DISCONNECT` だけが届いていた。`ble.c` はその `DISCONNECT` を捨てていたので、止まって見えた。再試行が有効な版でも、3 回失敗すると同じ経路で止まる（`0a0cfcf`〜`8061951` で数十分に 1 回止まった原因と見ている）。直しは、接続中に知らない接続番号の `DISCONNECT`（相手のアドレスが一致）を受けたら、接続失敗として枠を空けてスキャンに戻ること。`connect failed before the connect event` の行が出る。
- **`f102c45` の試験（事実）**：止まる不具合の直しは効いた。M5Dial の RST 5 回で止まり 0 回、起動直後の `0x3E` は 2 回出てどちらもすぐつなぎ直し、2 台そろうまで 4.9〜5.7 秒。Forget all devices からの 2 台のペアリングもできた。約 80 秒の 2 台の使用：切断 0、`lost=0`、`LAT` 最大 2.09 ms。新たに **G''**：リセット直後の MD600 が探索の途中で切った後、5 秒の見張りで切ってつなぎ直しても最初の探索に答えない状態が続き、1 分で 10 回くり返した（`a195bc8` では 30 秒待って 1 回つなぎ直すと成功していた）。MD600 のリセットと Pair new device で抜けた。
- **G'' の直し（`d2c4295`、`d2c4295` の試験で確認済み）**：同じ機器で探索が 2 回続けて止まったら、2 回目からは切らずに ATT の時間切れ（30 秒）まで待つ（`discovery stalled again (N in a row), keeping the link until the ATT timeout`）。時間切れで NimBLE が切り、つなぎ直す。入力を 1 つでも登録できたら回数を戻す。最悪でも `a195bc8` と同じ 35 秒で、最初の 1 回は 5 秒で回復を試す。
- **`d2c4295` の試験（事実、[報告](reports/m1-d2c4295-report.md)）**：**合格の基準をすべて満たした。** G''：探索の途中で MD600 が切った後、5 秒で 1 回つなぎ直し → 2 回目は接続を保って 30 秒の時間切れ → つなぎ直しで 0.7 秒で `subscribed 4`（つながり始めてから入力できるまで 36.7 秒）。10 分の連続使用：切断 0、2 台とも 7.50 ms・latency 0、`lost=0`、`LAT` 平均 0.72 ms・最大 1.93 ms（操作は断続的で、2 台同時は 18 秒）。電源の入れ直し 0.61〜0.69 秒、スリープからの復帰 0.62〜0.69 秒（ただし PC の復帰と重なり、M5Dial が動いたまま機器だけが起きる場面は未測定）。止まる不具合は 0 回。
- **`1fd6c6a` の試験（事実、段階 2、[報告](reports/m1-1fd6c6a-report.md)、ハブ経由）**：許可リストで待つ方式は動いた。書き込み後 1.25 秒で 2 台そろい、`scan start` はペアリングのときだけ。10 分の連続使用で切断 0（`LAT` 最大 2.37 ms、2 台同時 66 秒）。**M5Dial を動かしたままのスリープからの復帰**も合格（`connected` から `subscribed` まで 0.49〜0.53 秒）。ハブ経由のボタン＋RST も合格。止まる不具合 0 回。**不合格が 1 つ**：RST 3 回目で meteorite40 の `0x3E` が 2 回続いて 30 秒外され、2 台そろうまで 38.7 秒（`d2c4295` は約 5 秒）。**要確認が 1 つ**：機器側だけ BT クリアした meteorite40 が、ペアリングモードでないのに 0.46 秒の暗号化で通った。
- **`1fd6c6a` の 2 点の原因と直し（`e951dbc`。`e951dbc` の試験で確認済み）**：①`fe7b6a9` が `0x3E` を失敗の回数に数えていた → 数えるのは暗号化の失敗など、つなぎ直しても直らないものだけに戻した（`f90b5c7`）。②**本当の穴だった**：NimBLE の SM は、ボンド済みの機器に「鍵が無い」と言われると、アプリに知らせずに自分でペアリングし直す（`ble_sm.c` の `BLE_RESTART_PAIR`、Kconfig が無く既定 1）。`3c46caa` の「ペアリングモードのときだけ組み直す」は、この経路では一度も働いていなかった。ビルドの定義で 0 にした（`b8d689d`）。あわせて、暗号化が保存した鍵か新しいペアリングかをログに出す（`encryption on (stored key)` / `(new pairing)`、ペアリングモード外の新しい鍵は `WARNING`。`90d9ef4`）。③待ち受けの行は変化したときだけ出し、接続時に `connecting via accept list after N s of waiting` を出す（`e951dbc`）。
- **`e951dbc` の試験（事実、[報告](reports/m1-e951dbc-report.md)、ハブ経由）**：**合格の基準をすべて満たした。** RST 5 回で 4.66〜5.20 秒（`0x3E` が 1 回出ても外されない）。機器側だけ BT クリアした meteorite40 は、通常時は `device lost the bond` で切られ、2 回目で 30 秒外され、**一度も暗号化されなかった**（`WARNING` 0 回）。Pair new device で組み直せた。電源の入れ直しは `connecting via accept list` から 0.49〜0.52 秒で `subscribed`、暗号化はすべて `(stored key)`。止まる不具合・ホストのリセット・探索の止まり 0 回、`lost=0`、`LAT` 最大 2.41 ms。10 分の連続使用とスリープからの復帰は、この版ではしていない（`1fd6c6a` で合格）。**段階 2 は完了。**
- **`e951dbc` で分かったこと（残課題）**：①Pair new device で組み直すと、ポート番号（`hub_port`）が 2 から 3 に変わった。ボンド一覧の並び順を番号にしているため、消して登録し直すと末尾に回る。ポートごとの割り当てが外れるので、M2 の機器台帳（決定 I4：番号はアドレスに固定）で直す。②ペアリングモードで鍵を消した直後の 1 回目は、5 秒たっても暗号化されずに切られ、2 回目で通った（入力できるまで 7.4 秒）。組み直しを始める `ble_gap_security_initiate()` の戻り値を見ていないので、始められなかったか分からない（推測）。次の作業でログを足して確かめる。③手順書の「`(new pairing, replaced the stored key)` が出る」は誤り：1 回目の接続で古い鍵を消し、それが切れたので、2 回目は鍵の無い状態から始まり `(new pairing)` が正しい。④ペアリング情報の上限は 4 件（`CONFIG_BT_NIMBLE_MAX_BONDS=4`）。試験の最後で 3 件（MD600 の古いアドレスが残る件は M2）。
- **`a0d8f9e`・`a4c1b49`・`ff8e166` の試験（事実、IST Trackball と Cube Turner PRO、[報告](reports/)）**：UUID の補正の回帰なし。A1・A2・A4 は直った。**Cube Turner は RST 後に使えない**：5 秒で切る時点で接続は保存した鍵で暗号化済み（`link enc=1 auth=0 bonded=1 key_size=16`、鍵は Legacy で `sc=0`、`ediv_rand=set`）なのに、`ENC_CHANGE` が切るまで届かない。A3 は悪化（IST が巻き込まれて 43.7 秒）。
- **原因と直し（`9309d56`、未確認）**：Cube Turner はつながるとすぐ Security Request を送る。NimBLE はそれに保存した鍵で答え、`CONNECT` をアプリに渡す前（相手の機能と版を読む間）に暗号化を終えて `ENC_CHANGE` を出す。`ble.c` はまだその接続を知らず（`dev_by_handle` が見つけない）、知らせを捨てていた。そのあと `ble.c` の暗号化の要求が、暗号化済みの接続の上で止まっていた（切ったときに `security done status=0x0` と `encryption failed status=0x23d` がまとめて届いた）。直し：`CONNECT` の時点で接続が暗号化済みなら受け入れて探索へ。5 秒の見張りは自分の要求から数え、NimBLE の SM の空きを待つ間は数えない。
- **`9309d56` の試験（事実、[報告](reports/m1-9309d56-report.md)）**：Cube Turner は Pair new device なしで戻った（`before the connect event`、起動から 2.00 秒）。RST 3 回で 2.5〜8.3 秒、IST は切られず。10 分の連続使用で切断 0（`LAT` 最大 2.63 ms）、31 分間 2 台とも切断 0。残り：機器の Security Request が `CONNECT` の後に来た 4 回は、`enc=1 bonded=0 key_size=0` のまま知らせが届かず 5 秒で切られ、2 回目でつながった（電源の入れ直しで 7.7 秒）。
- **直し（`da3c37f`、未確認）**：暗号化を待つ間、毎秒その接続の状態を読み、`enc=1` なら受け入れる。無線チップはその機器用に保存した鍵でしか暗号化しないので、通常時に別の鍵で通る穴にはならない。受け入れた後に鍵が変わっていれば、通常時は `WARNING` を出して切る。
- **`da3c37f` の試験（事実、[報告](reports/m1-da3c37f-report.md)）**：合格の基準をすべて満たした。Cube Turner の電源の入れ直し 5 回は 1.7〜2.3 秒（全部 `device started pairing itself` → `noticed by polling`、最初の読み取りで `enc=1 bonded=0 key_size=0`）、RST 3 回は 2.6〜4.4 秒（Cube Turner は `before the connect event`）、5 分で切断 0、`WARNING` 0 回。受け入れた後の `ENC_CHANGE` は一度も来なかった。
- **安全面の確認（NimBLE のソース）**：`ble_sm_update_sec_state()` は `bonded` と `key_size` に 0 を書かないので、`enc=1 bonded=0 key_size=0` は「NimBLE が暗号化の知らせを自分の手続きと結びつけられなかった」印。通常時に登録済みのアドレスの接続が別の鍵で暗号化される経路は無い（無線チップは保存した LTK でしか暗号化を始めず、NimBLE が登録済み機器と新しくペアリングするのは、保存した鍵で暗号化が済んだ後の格上げか、通常時は断っている `REPEAT_PAIRING` だけ）。念のため、読み取りでの受け入れは「登録済みのアドレスで、保存した鍵の指紋が変わっていない」ときに限った。
- **知らせが失われる原因の候補（`f2093b6` で実験、未確認）**：NimBLE は `CONNECT` を渡した直後に毎回 LE Set Data Length を出す（コアの `ble_gap_event_connect_call()`、Kconfig で止められない）。S3 では暗号化の最中のデータ長変更が暗号化を壊す報告がある（esp-idf#19057）。失われた知らせはすべて、暗号化が `CONNECT` をまたいだ接続だった。起動時に無線チップの既定値を同じ 251 バイト・2120 µs にして、接続ごとの要求で何も変わらないようにした。
- **M5Dial の再起動の訂正**：`d2c4295` で見た「PC のスリープ中に M5Dial が再起動した」は、PC が休止状態に移って USB の電源が切れたため、`1fd6c6a` の中断中の再起動は PC の再起動（20:27）によるもので、どちらも M5Dial 側の問題ではない（利用者が Windows のイベントログで確認。推測を含む）。
- **G' の直し（`eb9a5af`。`f102c45`・`d2c4295` の試験で見張りが働くことを確認）**：探索中に GATT の返事が 5 秒来なければ切ってつなぎ直す。原因が機器側（リセット直後の MD600 が最初の要求に答えない）か本体側（NimBLE の ATT に前の接続の手順が残る）かは未確定。
- **G の原因と直し（`a195bc8`、`a195bc8` の試験で「紛れ込み」の解消を確認）**：切れた接続の GATT 手順の完了が、同じ接続番号を使い回した次の接続の手順として届き、探索の状態を壊していた。GATT 手順に接続の世代を付けて古い結果を捨てる。保険として、探索後に入力 Report を 1 つも登録できなかった暗号化済みの接続は、その場で切ってつなぎ直す。
- **`0a0cfcf` の試験（事実）**：接続の試みが止まる不具合が自然に再現し、25 秒で BLE ホストをリセットして **RST なしで復旧**した。30 秒避ける・再ペアリングを断る、も動いた。新たに：A. リセット後や 30 秒の待ちが明けた後、ペアリング済みの機器が Pair new device を押すまで見つからない（1 時間以上）。B. 別の機器のペアリング中に正しい鍵の機器が `security start failed rc=0x6` で避けられる（2 回）。C. 鍵を消して黙っている機器が 30 秒枠を占める。D. ホストのリセットで正常な接続も切れる。E. 途中までの Report Map をコアに渡した。F. `cancel` の行が毎秒出る。
- **原因と直し（`8061951`、未確認）**：A は探索の重複フィルタ（`filter_duplicates=1`）。コントローラーは 1 回の探索で同じアドレスを 1 度しか報告しないため、避けている間に報告された機器は探索を始め直すまで報告されない → フィルタを外した。B は NimBLE がペアリング／暗号化の処理を同時に 1 つしか持てないため（`BLE_SM_MAX_PROCS=1`）→ 切らずに毎秒再試行。C は 5 秒で切って避ける。E・F は直した。D はそのまま（A が直れば自動でつながり直す見込み）。
- **`09b3075` で見つかった接続まわりの問題（事実）と直し（`0a0cfcf`、`8061951` の試験で確認済み）**：①機器が広告の直後に消えると、接続の試みが完了せず探索が止まった（2 回、RST で復旧）。NimBLE は取り消し後の完了イベントを待ち続ける既知の穴があるため、15 秒で取り消し、25 秒で BLE ホストをリセットする。②暗号化に失敗した機器が約 65 ms〜0.4 秒周期で再接続をくり返し（2 分で 280 回）、ほかの機器を探せなかった → 30 秒避ける。③`security start failed rc=0x6` の接続が切られずに枠を占めた → 切る。④ペアリング済みのアドレスを名乗る機器の再ペアリングを無条件に受け入れていた → ペアリング待ちのときだけ受け入れる。
- **暗号化に失敗した接続を持ったままにすると枠が埋まる**（事実）。機器側に古い鍵が残っていると `encryption failed`（`0x503`／`0x505`）のまま接続が残る。次の版では本体から切る。機器側でペアリングを消してもらう必要は変わらない。
- **本家のポート番号はペアリングの順で入れ替わる**（事実。1 回目は MD600＝1、meteorite40＝2。Forget all devices 後は逆）。本家どおりで、M2 の決定 4（住所に固定＋手動での付け替え）で直す。
- **meteorite40 は再ペアリング後に latency 30 を求めてきた**（事実。`itvl=6-12 lat=30`）。7.50 ms・latency 30 で受けた。それまでの接続では要求は来なかった。latency は機器が省電力のために間引いてよい回数で、入力があるときは即座に送れるので遅れには効かない見込み（推測）。本家 BLE 版も機器の latency を受け入れる。影響は A8 の測り直しで見る。
- **書き込みでペアリング情報と設定が消えなくなった**（事実。NVS をアプリの後ろ `0x400000` に移した効果。Q31 では毎回消えた）。

## 4. 途中で分かったこと（次の人向け）

| 事実 | 対応 |
| --- | --- |
| ESP32-S3 の USB コントローラーは送信用の FIFO が IN endpoint 0〜4 の 5 本だけ（TinyUSB `dwc2_esp32.h`）。0x85 を使うと 1 バイトも出ない | HID 2 つと CDC で 0x81〜0x84。これ以上 IN endpoint は足せない |
| 本家の設定ツールは USB の製品名に `Bluetooth` が入っていないと Pair new device / Forget all devices を出さない（`config-tool-web/code.js`） | 製品名を `HID Remapper Bluetooth XXXX` に |
| ESP-IDF の再起動は USB シリアルをリセットしない。再起動前に USB シリアルの状態をいじる直し（`db94be3`）は、書き込みモードを PC から見えなくした。ボタン＋RST・1200 bps・電源の入れ直しでも復旧せず、**M5StampS3 の G0 を押しながら電源を入れる**（背面を開ける）でだけ復旧した | 取り消した。USB シリアルをいじる直しは G0 に手が届く状態で試す |
| `esp_tinyusb` 2.x は TinyUSB を必ず自分のタスクで回す | `espressif/tinyusb` を直接使い、主ループで回す（決定 I2） |
| 本家 BLE 版の 1 ms の刻みは USB の SOF（`status_cb`）。設計書の決定 2 の「`esp_timer`（本家 BLE 版と同じ）」の括弧内は事実と違う | M1 は決定どおり `esp_timer`。設計書は要修正 |
| 本家 BLE 版は報告の先頭に報告 ID を常に付けてコアに渡すが、報告 ID を使わない機器では 1 バイトずれる | `external_report_id` で渡す |
| 機器側でペアリングを消してやり直すと、MD600 はアドレスが変わる（`1f:64` → `26:27` → `5a:1d`） | M2 の決定 4 の「手動での付け替え」の根拠 |
