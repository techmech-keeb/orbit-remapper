# M1 の報告：版 `728105c`（`orbit-m1-728105c-A1-usb-only.bin`、2026-09-27）

利用者の PC（Windows 11）と初代 M5Dial で、[m1-handoff.md](../m1-handoff.md) §6.1 を確かめた。PC 側の USB の見え方は PowerShell（`Win32_PnPEntity`）、ログは `System.IO.Ports.SerialPort`（115200 bps、DTR/RTS あり）。`.bin` の SHA-256 は引き継ぎ文書の値と一致。**M5Dial は PC 本体のポートに直接つないだ。**

## 結論

- **§6.1 の 1（ボタン＋RST で書き込みモードに入る）：不合格。** 画面は `DOWNLOAD MODE` だったと利用者は記憶している（作業を中断して時間が空いたため、確実ではない）。PC からは**何も見えなくなった**（VID 303A も VID CAFE も「Unknown USB Device」も現れない）。15 分待っても同じ。**PC の再起動でアプリとして復旧**（ケーブルの抜き差しだけで直ったかは未確認）。前の版 `3662016` は同じ操作・同じポートで合格していたので、**`728105c` の直し（書き込みモードの前に USB シリアルを 0.5 秒切り離してつなぎ直す）で壊れた**と見ている。引き継ぎ文書 §5 の「切り離したまま再起動すると、書き込みモードに入っても PC から見えない」がそのまま起きている可能性が高い（推測）。
- **§6.1 の 2（ログ）：不合格だが、原因の手がかりあり。** 本体の画面は `LOG DTR 2K` と `LOG LOST 21K`（黄）。PC 側は、ポートを開き直して DTR/RTS を立てても **0 バイト**。「2K」は `CFG_TUD_CDC_TX_BUFSIZE 2048` と一致するので、**TinyUSB の CDC の送信バッファ（2 KB）を満たしたあと、USB へ 1 バイトも出ていない**と見ている。送信の口 `EP 0x85`（IN）の転送が始まらない、または終わらない。
- USB の複合機器としての認識（HID 0、HID 1、CDC）と、RST だけの再起動後の復帰は、前の版と同じく正常。
- 画面：`ORBIT M1 728105C` / `USB OK` / `LOG DTR 2K` / `HEAP 213K MIN 208K` / `LOG LOST 21K`。

## 直してほしいこと

1. **ボタン＋RST の経路を `3662016` の動きに戻す**か、USB シリアルのつなぎ直しが確実に効いてから再起動するようにする。`3662016` では PC 本体のポートで合格していた。ハブ対策（0.5 秒の切り離し）は、本体のポートでの動作を壊さない形で入れ直す。確認の順番は「本体のポートで合格 → ハブで試す」。
2. **CDC の送信が USB へ出ていない。** 確かめてほしい点：
   - `tud_cdc_write_flush()` のあとに `EP 0x85` の転送が始まっているか（`usbd_edpt_busy` の状態、`tud_cdc_tx_complete_cb` が呼ばれるか）。
   - `CFG_TUD_DWC2_DMA_ENABLE 1` のとき、CDC の送信バッファが DMA で読める領域にあるか。試しに DMA を切った版（`CFG_TUD_DWC2_SLAVE_ENABLE` だけ）で動くか。
   - `tud_task_ext(0, false)` が主ループで十分な頻度で回っているか（HID の送信も同じ経路なので、ここが止まっていると A2 以降も動かない）。
   - 送信の口の数は問題ない（TinyUSB の ESP32-S3 向け `DWC2_EP_MAX` は 7、この版は 0x85 まで）。
3. 次の版では、**`START` 行と 1 秒ごとの `SUM` 行が PC に届くこと**を、書き込みモードの試験より先に確かめたい。ログが取れないと、以後の試験の判定ができない。
