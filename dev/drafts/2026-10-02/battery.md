# 接続した機器の電池の残量（検討と段階 0・1）

状態：段階 0 は IST Trackball の分だけ試験済み（[bat0-8153e8b-report.md](../2026-09-27/reports/bat0-8153e8b-report.md)）。段階 1（表示）を作り、試験待ち。2026-10-02 作成、同日更新。

## 1. 何を作るか

機器を PC に直接ペアリングすると、PC が機器の Battery Service（0x180F）を読んで残量を出す。Orbit を挟むと PC からは USB のキーボード・マウスに見え、残量は Orbit で止まる。そこで Orbit が機器の Battery Service を読み、Orbit の画面と、設定ツール向けの命令に出す。

PC の OS に電池として見せる案（USB の HID 記述子に Battery Strength を足す）は見送る。記述子は本家コアのもので、足すと本家の改造になる。Windows が USB の機器の電池をこの方法で表示するかも確かめていない。

## 2. 決めたこと（2026-10-02）

| 項目 | 決定 |
| --- | --- |
| 読み方 | HID の入力が届くようにし、機器の情報を読み終えてから、Battery Service を探す。一度読み、通知に対応していれば登録する。通知の無い機器は 10 分ごとに読み直す（入力が 1 秒途切れたときだけ） |
| 値の置き場 | メモリだけ。NVS には書かない。切れた機器は表示を消す |
| 画面 | カードの 1 行目、名前の右に電池の印と %。Battery Service の無い機器は何も出さない |
| 色 | 30% 以上はふつう、11〜29% は黄、10% 以下は赤 |
| 少ないとき | 10% 以下になった時に 1 回だけ、状態の行に `Port N battery low (8%)`。リングの色は変えない。消えている画面はつけない |
| PC から | `GET_STATE`（0x80）の後ろに枠ごとの残量を足す（不明は 255）。設定のページで表示する |
| 順番 | 段階 0 を 2b の前にやる。段階 1 は段階 0 の結果を見て決める |

## 3. 段階 0：調べる

### 作ったもの

`firmware/orbit/main/ble.c` に、Battery Service を調べる処理を足した。画面にはまだ出さない。ログだけ。

- 機器の情報（名前・製造者・型番・PnP ID）を読み終えたら、1 回だけ動く。
- Battery Service を探し、その中の Battery Level（0x2A19）を最大 4 つまで集める。
- それぞれについて、記述子（CCCD 0x2902、User Description 0x2901、Presentation Format 0x2904）を探し、値と、User Description と Presentation Format を読む。
- 通知に対応していれば登録し、届いた通知をログに出す。**電池の通知は入力として本家コアに渡さない**（今までは届いた通知をすべて入力として渡していた）。

ログの行（どれも `M1 EVT ... battery` で始まる）：

| 行 | 意味 |
| --- | --- |
| `battery: N Battery Service(s)` | Battery Service の数。0 なら、その機器は残量を出さない |
| `battery: N Battery Level characteristic(s)` | 残量の値の数。分割キーボードは 2 つあるかもしれない |
| `battery K: handle=... read=1 notify=1 cccd=1 user_desc=0 presentation=1` | 値ごとの性質 |
| `battery K: level=80% (1 byte(s))` | 読んだ残量 |
| `battery K: user description="..."` | 値の説明（分割キーボードの左右など） |
| `battery K: presentation format=... description=0x....` | 値の説明（番号で表すもの） |
| `battery K: notifications on` | 通知を登録できた |
| `battery K notify level=79% (1 byte(s)) after 612.3 s` | 機器から届いた通知。つないでからの秒数つき |
| `battery: probe done` | 調べ終わった |

### 試験の手順

機器：IST Trackball、Mistel MD600、機器 B（手元にあれば、ほかの BLE 機器も）。

1. 書き込んで起動し、ログを `dev/tools/serial-capture/` で残す。
2. 3 台をつなぐ（同時に 2 台まで。1 台ずつ入れ替えてよい）。機器ごとに、上の `battery` の行を全部抜き出す。
3. 読めた残量と、機器の側の表示（あれば。メーカーのアプリ、LED、PC に直接つないだときの値）を見比べる。
4. 1 台はつないだまま 30 分以上使い、通知（`notify`）が届くか、どのくらいの間隔か、値がどう変わるかを見る。
5. 電池を調べる処理の前後で、入力が遅れないか。`LAT` の行で、3 ms を超える秒が増えていないか。調べる処理は、つないだ直後の 1 秒以内に終わる見込み（推測）。
6. 調べる処理のあとも、入力・切断・つなぎ直しが今までどおりか。

### 報告に書くこと

- 機器ごとに：Battery Service の数、Battery Level の数、read／notify、説明の有無と中身、読めた値、機器の側の値。
- 通知が届いた機器：最初の通知までの時間、間隔、値の変わり方。
- `LAT` の様子（調べる処理の前後）。
- 何かおかしなこと（ログの抜粋）。

報告は `dev/drafts/2026-09-27/reports/bat0-<版>-report.md` に置く。機器のアドレスは下位 2 バイトだけにする。

## 4. 段階 1：表示する

### 段階 0 からわかったこと

IST Trackball の分だけ（Mistel MD600 と機器 B は手元に無く、あとで同じ版で試す）。Battery Service 1、Battery Level 1、`read=1 notify=0 cccd=1`、説明なし、70%。調べる処理はつないでから 0.5〜0.7 秒で終わり、`LAT` は悪くならなかった。

### 決めたこと（2026-10-02）

| 項目 | 決定 |
| --- | --- |
| CCCD はあるが通知に対応していない（IST） | **登録しない。読み直す側に入れる。** 通知できるかは性質（properties）の Notify で決まり、CCCD があるだけでは足りない。性質で宣言していない通知を CCCD に書いて頼むのは、機器が想定していない使い方になる。読み直しで残量は取れるので、登録しに行く得は無い。確かめるために、ログの行に性質の値（`props=0x..`）を足した |
| 値が 2 つ以上ある機器 | 画面・`orbit list`・`GET_STATE` には**いちばん低い値**を出す（先に切れる側）。ログには値ごとに出す。分割キーボードでまだ試していないので、試してから見直す |
| 読み直しの間隔 | 通知していない値は 10 分ごと。入力が 1 秒途切れるまで待つ（§2 のとおり） |
| 少ないときの知らせ | 10% 以下になったとき、つながっている間に 1 回。15% 以上に戻ったら（充電）、次に 10% 以下になったときにまた知らせる。状態の行に 1 分出す。質問・台帳がいっぱい・ペアリング中のときは、そちらを優先する |
| 値がおかしいとき | 101 以上は不明として扱う（画面に出さない） |
| `GET_STATE` | 最後に枠ごとの残量（%、不明は 255）を足した。版 1 では 0 だったバイトなので、設定ツールとのやりとりの版（`PROTOCOL_VERSION`）を 2 にした |

### 作ったもの

| 場所 | 中身 |
| --- | --- |
| `ble.c` | 読んだ値をメモリに置く。通知していない値の読み直し。少ないときの知らせ。ログの行：`battery 0: reread level=70% (1 byte(s)) after 600.4 s`、`battery low 8% (port 1)`、`battery: probe done lowest=70% updates=reread` |
| 画面（`ui.c`） | カードの 1 行目の右に電池の印と %。30% 以上はふつうの色、11〜29% は黄、10% 以下は赤。Battery Service の無い機器と、まだ読んでいない機器は何も出さない。名前は、そのぶん短く切る。知らせは状態の行に赤で `Port 1 battery low (8%)`。リングの色は変えず、消えている画面はつけない |
| `orbit list` | 行に `battery=70`。つながっていない・Battery Service が無い・まだ読んでいない機器は `battery=-` |
| `GET_STATE` | 上の表のとおり |
| 試験用の命令 | `orbit battery <ポート> <%>`：その機器の残量を、次に本当の値を読むまで（読み直しか通知まで）指定の値にする。色と知らせを確かめるため |

### 試験の手順

機器：IST Trackball（手元にあれば、ほかの BLE 機器も）。

1. 書き込んで起動し、ログを `dev/tools/serial-capture/` で残す。
2. IST をつなぐ。`battery: probe done lowest=..% updates=reread` が出ることと、カードの名前の右に電池の印と % が出ることを確かめる。名前が読める長さで残るか、写真を撮る。
3. `orbit list` を打ち、IST の行が `battery=<%>` になることを確かめる。
4. 30 分以上つないだまま、ふだんどおりに使う。`battery 0: reread level=` の行が約 10 分ごとに出ることと、値が画面と合うことを確かめる。ボールを回し続けている間は読み直しが待たされ、止めて 1 秒たってから読むことも見る（行の時刻と、前後の入力の様子）。
5. 読み直しの前後で `LAT` が悪くならないか（3 ms を超える秒が増えていないか）を見る。
6. 色と知らせ：`orbit battery 1 25` → 黄、`orbit battery 1 8` → 赤と、状態の行に `Port 1 battery low (8%)` が 1 分出る。`orbit battery 1 5` → もう一度は出ない。`orbit battery 1 50` → ふつうの色。`orbit battery 1 9` → もう一度出る（15% 以上に戻ったため）。ポート番号は `orbit list` で確かめる。途中で 10 分ごとの読み直しが入ると本当の値に戻る（ログの `reread` の行でわかる）。そのときは打ち直す。
7. 画面を消える設定にして、消えている間に `orbit battery 1 50` → `orbit battery 1 8` と打つ。画面がつかないことを確かめる。
8. IST の電源を切る → カードの電池の表示が消え、`orbit list` が `battery=-` になる。電源を入れ直すと、また読んで表示する。
9. ペアリング中（メニューの「Pair new device」）に `orbit battery 1 50` → `orbit battery 1 8` と打つ。状態の行はペアリングの表示のままになることを確かめる。
10. 入力・切断・つなぎ直しが今までどおりか。

### 報告に書くこと

- 2〜3：probe の行、カードの見え方（写真）、`orbit list` の行。
- 4〜5：読み直しの時刻と値、入力が続いているときに待たされたか、`LAT` の様子。
- 6〜9：色と知らせが手順のとおりになったか。違ったときは、ログの抜粋と画面の写真。
- 何かおかしなこと（ログの抜粋）。

報告は `dev/drafts/2026-09-27/reports/bat1-<版>-report.md` に置く。機器のアドレスは下位 2 バイトだけにする。
