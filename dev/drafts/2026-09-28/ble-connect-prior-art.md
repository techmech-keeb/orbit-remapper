# 複数の BLE 機器を安定して検出・接続する先行事例

M1 で工数がかかっている「S3 で 2 台をすんなり見つけて、つなぎ直す」処理について、規格・OS・他のマイコンのファームウェア・ESP32 の実装・市販品を調べた記録。2026-09-27〜28 に、各プロジェクトのソースコードと仕様書を取得して読んだ。**Orbit の実機では何も試していない。** 出典は [sources.md](../2026-09-26/sources.md#ble-の検出接続の先行事例2026-09-28-確認)。反映の計画は [ble-connect-plan.md](ble-connect-plan.md)。

## 1. 結論

- **一番の参考は本家 HID Remapper の Bluetooth 版**（`firmware-bluetooth/`）。nRF52840 上の Zephyr で書かれ、MIT ライセンス。Orbit と同じ本家コアを使い、ボンド済みの機器を最大 8 台同時につなぐ。コードではなく手順を移植すればよい（BTstack は使っていない）。
- 規格（HOGP）、Linux・BlueZ、Zephyr、Nordic の nRF Desktop、ZMK、RMK、BlueRetro の再接続は、ほぼ同じ型をしている（§2）。
- **今の Orbit は多くの点で型どおりだが、何か所か外れている**（§5）。その外れ方が、これまでの問題 A（検出が止まる）、1（接続が止まる）、2（再試行の嵐）、G'（最初の探索に返事がない）の一部を説明できそう（推測）。
- **2 台を同時に USB へ中継する ESP32 の公開実装は見つからなかった。** 部品ごと流用できる既製品はない。

## 2. 実績のある実装に共通する型

| 型 | 採っている実装 |
| --- | --- |
| 接続の試みは常に 1 本。スキャンと同時に動かさない | Linux（「多くのコントローラは同時にできない」とコメント）、Zephyr、nRF Desktop、ZMK、RMK、esp-nimble-cpp、Espressif の `ble_conn_mgr` |
| ボンド済みの機器はアドレスで絞る。コントローラの許可リスト（Filter Accept List、旧称 White List）か、アプリ側の照合 | HOGP §5.2.2 が許可リストを推奨。Linux、BlueRetro、RMK、TrouBLE は許可リスト。ZMK、nRF Desktop、本家 BLE 版はアプリ側の照合 |
| ペアリングのときだけ「HID の機器なら誰でも」に絞りを緩める。全台つながったらスキャンを止める | 本家 BLE 版、nRF Desktop |
| 相手を名指しする広告（ADV_DIRECT_IND）はすぐ接続する | 本家 BLE 版、ZMK、BlueRetro、Linux（接続方針 DIRECT） |
| 接続したら最初に暗号化する。失敗したらボンドが失われたと判断する。自動では組み直さず、利用者の操作で再ペアリング | HOGP §5.2.4〜5.2.5（shall）、nRF の central_hids、RMK のドングル |
| 暗号化が済んでから探索する | central_hids、finger563/esp-usb-ble-hid（「早すぎると失敗し、ボンドまで消えた」とコメント） |
| 探索は同時に 1 台だけ。その間はスキャンを止める | nRF Desktop |
| 探索が段階のどこかで失敗したら、その場で切断して再接続に回す（粘らない） | nRF Desktop、ZMK、RMK |
| 同じ機器への接続の試みに回数の上限を付ける | nRF Desktop（1 台 2 回まで）、BlueRetro |
| 切断したら、その接続の状態をすべて捨てる。0.5〜1 秒待ってから再スキャン | ZMK、RMK（0.5 秒）、本家 BLE 版（1 秒） |
| スキャンの頻度を段階で変える。切断直後の 30 秒は 60 ms 間隔・30 ms 窓、その後は 1.28 秒間隔・11.25 ms 窓 | HOGP §5.2.3〜5.2.5 |
| 入力が流れている間はスキャンを止め、最後の入力から 1 秒後に再開する | 本家 BLE 版 |
| ボンド済みの相手のサービス情報を保存し、再接続では探索を省く | BlueZ（`Cache = always` が既定）。規格上もボンド済みの相手なら接続をまたいで有効（Core 5.4 Vol 3 Part G §2.5.2）。**組み込みの実装はどれもまだ保存していない**。本家の `BLUETOOTH.md` は「保存すれば再接続が速くなる」と課題に挙げている |

## 3. 事例ごとの要点

### 3.1 本家 HID Remapper の Bluetooth 版（MIT）

`firmware-bluetooth/src/main.cc`（最終変更 61b3f74、2025-01-17。master の先端は 51ab8b3）。Orbit に取り込んだ `firmware/hid-remapper/firmware-bluetooth/`（51ab8b3）でも、設定（`prj.conf`）、1 秒の再スキャン待ち、接続条件、暗号化の要求を確かめた。

- 設定：同時接続 8、ボンド 32（古いものから上書き）、自分のアドレスを変える機能（`BT_PRIVACY`）あり。
- スキャン：受動スキャン。通常時は「HID サービスの UUID を出していて、かつボンド済みのアドレス」だけに接続する。ペアリングのとき（ボタン、設定ツール、ボンドが 0 件）は UUID だけで絞る。ボンド済みが全部つながったらスキャンを止める。
- 絞り込みに一致しない ADV_DIRECT_IND は、スキャンを止めてすぐ接続する（コードに「未検証」のコメントあり）。
- 入力レポートを受けている間はスキャンを止め、最後のレポートから 1 秒後に再開する。切断、接続失敗、探索の完了・失敗の後も 1 秒後に再スキャン。
- 接続後：暗号化（Zephyr の `BT_SECURITY_L2`）→ HID サービスの探索 → 全入力レポートの購読 → Report Map の読み出し。接続条件は 7.5 ms・latency 44・監視タイムアウト 4 秒。
- 表示：LED の点滅回数で接続台数、点灯しっぱなしでペアリング中。ボタン長押し（3 秒超）で全ボンドを消す。
- 別ブランチ `bluetooth-classic`（Pico W、BTstack、Classic 専用）もある。こちらは BTstack なので流用しない。接続の試みに 12 秒の上限を付け、同じ相手への再試行は 5 秒空ける、という考え方だけ参考にする。

### 3.2 規格：HID over GATT Profile（HOGP）1.0

2011-12-27 採択。現行は 1.1（採択日は要確認）。

- 機器の側（§5.1.3）：ボンド済みの機器が自分から再接続するときは、名指しの広告を 1.28 秒か、誰にでも向けた広告を 30 秒・20〜30 ms 間隔で出す。その後は機器しだい。
- ホストの側：
  - §5.2.2：ボンドした機器のアドレスを許可リストに書き、許可リストの機器からの広告だけを処理する方針を推奨。
  - §5.2.3：常時待つスキャンは 1.28 秒間隔・11.25 ms 窓。これより粗くしない。
  - §5.2.4〜5.2.5：切断直後から 30 秒は 30〜60 ms 間隔・30 ms 窓。
  - 接続したら必ず暗号化して、ボンドが生きているか確かめる。失敗したときだけ、再ペアリング、探索、CCCD（通知の有効化設定）の書き直しをする。
  - §5.2.6：探索と暗号化の間は、接続間隔 7.5〜50 ms を推奨。
- Reconnection Configuration Service は廃止（Withdrawn）。
- Core 5.4 Vol 3 Part G §3.3.3.3：ボンド済みの相手の CCCD は接続をまたいで保持される（shall）。

### 3.3 Linux カーネルと BlueZ

- BlueZ の HID（HoG）は自動接続の対象。カーネルは接続待ちの機器を一覧に持ち、一覧が空でなければ許可リスト付きの受動スキャンをする。一覧の機器から広告が来たら直接接続する（既定 20 秒の上限）。
- 接続中はスキャンを再開しない。接続の試みが進行中なら、2 本目は出さずに待つ。
- 許可リストの変更はスキャンを止めてから行う。容量を超えたら絞らないスキャンに切り替える。
- 相手が変わるアドレス（RPA）を使うときは、相手の鍵（IRK）をコントローラの解決リストに先に入れ、許可リストには相手の固定の身元アドレスを入れる。
- サービス情報は既定で保存（`main.conf` の `Cache = always`）。Database Hash が一致すれば探索を省く。再接続で HID の仮想デバイスがすでにあれば、CCCD を書き直さない。

### 3.4 Zephyr

- `bt_conn_le_create_auto` は許可リストでの接続。1 回で 1 台だけつなぐので、残りの機器にはつながった後にもう一度呼ぶ。
- 許可リストは、スキャン・広告・自動接続のどれかが使っている間は変更できない。
- `BT_GATT_AUTO_RESUBSCRIBE`（既定で有効）は、相手が CCCD を忘れた場合に備えて再接続時に書き直す相性対策と説明されている。

### 3.5 Nordic nRF Connect SDK（ライセンスは Nordic 5 条項。Nordic 以外のチップでの利用に制限があるので、考え方だけ参考にする）

- **nRF Desktop のドングル**（マウスとキーボードを同時に受ける。今回の用途に一番近い）：
  - ボンド済みはアドレスで絞り、ボンドに空きがあるときだけ名前で新しい機器を探す。
  - 接続数が上限のときと、**探索中はスキャンを止める**。探索は同時に 1 台だけ。
  - 探索の各段階で失敗したら、すぐ切断する。
  - 接続の試みは 1 台につき 2 回まで（`BT_SCAN_CONN_ATTEMPTS_FILTER`、既定で有効）。繰り返し失敗する機器がスロットを占め続けるのを防ぐ。
  - スキャンは 30 秒、機器が無操作になって 5 秒でスキャン再開。
- **central_hids**：接続したら暗号化を要求し、暗号化の成功を受けてから探索する。暗号化に失敗したら探索しない。

### 3.6 ZMK と RMK（キーボードの分割の親側）

- ZMK（MIT）：空きがあればスキャンし、保存したアドレスに一致したらスキャンを止めて接続。探索が済んだらスキャンを再開して次の機器へ、と順番につなぐ。切断時にハンドルなどを全部 0 に戻す。許可リストは使っていない。
- RMK（MIT/Apache-2.0、手元の `rmk/rmk/src/split/ble/central.rs`、コミット 568770f）：接続待ちの全アドレスを 1 つの許可リストにまとめ、接続を 1 回だけ要求する。**先に応答した機器がつながるので、電源の切れた機器が他を塞がない**。全体に 15 秒の上限。切断後は 0.5 秒待つ。スキャンを止めたと確定してから接続する（「止まる前はコントローラが接続を断る」とコメント）。

### 3.7 ESP32 の実装

- **Espressif `ble_conn_mgr`**（esp-iot-solution、v1.3.1、2026-09-09、Apache-2.0、NimBLE 専用）：接続の試みは常に 1 本、接続前に必ずスキャンを止める、接続の上限 30 秒。ボンドから許可リストを作り直す関数がある（v1.2.1 から）。**自動再接続は持たない**。HID ホストもない。版が若く、部品ごと使うより作りの参考にとどめる。
- **esp-nimble-cpp / NimBLE-Arduino**（Apache-2.0）：接続の見張りを自分で持ち、時間切れで接続を取り消す（NimBLE の内部タイマーに頼らない）。接続イベントの接続番号が自分のものと一致するか確かめて、古い接続宛てのイベントを捨てる。
- **finger563/esp-usb-ble-hid**（MIT、S3）：同時は 1 台。5 秒で区切ったスキャンを繰り返す。暗号化は 3 秒ごとに要求し直し、15 秒で諦めて切断。暗号化の後に探索する。
- **esp32beans/BLE_HID_Client**（MIT）：再接続ではサービス情報を取り直さない。
- **ESP-IDF 標準の HID ホスト（`esp_hidh`）**：v5.5.5 では Report Map を読まない不具合がある（esp-idf#19011、修正は v5.5.5 より後）。2 台目のデータが読めない問題は未解決（esp-idf#11312）。接続を待つ処理が上限なしで止まり、探索の状態を 1 か所に持つので、同時に複数を開く作りになっていない。

### 3.8 市販品と周辺機器の振る舞い

- Logi Bolt（公式ホワイトペーパー）：受信機にペアリング 6 台、同時接続 3 台。再接続は受信機経由で 300 ms、OS 直結の Bluetooth では 2 秒超。
- Keychron：10 分無操作でスリープ、キーを押すと約 3 秒で再接続（公式の説明）。広告の種類とアドレスの方式は非公開。
- Mistel：一次情報は見つからなかった。
- 周辺機器の再接続の広告は短い（名指しの広告は 1.28 秒）。スキャンの窓が狭いか、スキャンを止めていると取り逃がす。

## 4. ESP32-S3 と NimBLE v5.5.5 で分かったこと

ESP-IDF v5.5.5 のソースと Orbit の `sdkconfig` で確かめた（2026-09-28）。

| 項目 | 事実 | Orbit への影響（推測を含む） |
| --- | --- | --- |
| 接続失敗時の自動再試行 `BT_NIMBLE_ENABLE_CONN_REATTEMPT` | S3 では既定で有効、3 回まで。Orbit も有効。接続確立の失敗（0x3E）で切れると、NimBLE は **切断イベントをアプリに渡したうえで、自分でも接続をやり直す**（`ble_hs_hci_evt.c`）。アプリには `BLE_GAP_EVENT_REATTEMPT_COUNT` が届くだけで、Orbit はこれを扱っていない | Orbit が切断を受けて自分でもスキャン・接続を始めると、NimBLE のやり直しとぶつかる。問題 1（接続が止まる）、2（再試行の嵐）の一因の可能性 |
| スキャン重複キャッシュ | 機器単位（`SCAN_DUPL_TYPE_DEVICE`）、消す周期 0（`DUPL_SCAN_CACHE_REFRESH_PERIOD=0`）。スキャンを止めるまで消えない | 問題 A の原因。Orbit はスキャンを始めるときに重複除去を使わない設定（`filter_duplicates = 0`、`be58153`）にして回避済み |
| 許可リストでの接続 | `ble_gap_connect()` に接続先を空で渡すと許可リストを使う。`BT_NIMBLE_WHITELIST_SIZE` は 12 | 使える |
| 相手のアドレス解決 | ソフト側での解決（`BT_NIMBLE_HOST_BASED_PRIVACY`）は初代 ESP32 専用。S3 はコントローラの解決リストを使う | 解決リストの件数は要確認 |
| サービス情報の保存 `BT_NIMBLE_GATT_CACHING` | v5.5.5 にある。Orbit は無効 | 探索の省略に使える可能性。Database Hash を持たない機器でどう動くかは要確認 |
| スキャン中の接続 `BT_NIMBLE_HOST_ALLOW_CONNECT_WITH_SCAN` | S3 で選べる。近い世代の C3 で、スキャン中に接続すると落ちる報告がある（esp-idf#18063、未修正） | 使わない |
| 多台接続の例題 `ble_multi_conn` | 対象は C5 / C6 / C61 / H2。README に「ESP32 / C3 / S3 / C2 は必要な独自 HCI を持たない」 | 使えない |
| SM の同時手順 `BLE_SM_MAX_PROCS` | 1 に固定（M1 で確認済み） | 暗号化は 1 台ずつ |

未修正の不具合（2026-09-28 時点で Open）：

- **esp-idf#18893**：S3 のセントラルで暗号化した直後から GATT の通信が流れず、監視タイムアウト（0x08）で切れる。v5.5.3 / v5.5.5 で再現。報告者は「C6 のライブラリにある修正が、S3 と共通のライブラリに無い」と指摘している。**G'（つなぎ直した接続の最初の探索に 30 秒返事がない）と症状が似ている**が、同じものかは要確認。
- **esp-idf#19057**：S3 でボンド済みの機器に再接続するとき、データ長の変更（LE Set Data Length）を暗号化より先に行うと、暗号化が時間切れ（0x08）になる。回避策はデータ長の変更を暗号化の後に回すこと。Orbit のコードはデータ長を変えていない。NimBLE やコントローラが自動で変えているかは要確認。
- esp-idf#19030：NimBLE の NVS 保存が既存の記録の上書きを保存しない（報告は v6.0.2。v5.5 でも同じかは要確認）。
- esp-idf#14053：S3 の NimBLE で 0x28（INSTANT_PASSED）で切れる。

## 5. Orbit の今の作りとの差

| 項目 | 今の Orbit（`firmware/orbit/main/ble.c`） | 型 |
| --- | --- | --- |
| 再接続の見つけ方 | 自前のスキャンとアドレス照合（`peers_only`） | 許可リストへの 1 回の接続要求（RMK）、またはスキャンして一致したら止めて接続（ZMK、nRF Desktop） |
| 接続の管理 | 接続は 1 本ずつ、接続前にスキャンを止める（型どおり）。ただし NimBLE の自動再試行も裏で接続を始める | アプリが一元管理 |
| 探索中のスキャン | 止めていない（空きスロットがあればスキャンを続ける） | 止める（nRF Desktop） |
| 失敗した機器 | 30 秒避けるリスト | 1 台あたりの試行回数に上限（nRF Desktop） |
| 探索 | 毎回すべて探索 | ボンド済みなら保存した情報で省く（BlueZ、規格） |
| スキャンの頻度 | 常に 60 ms 間隔・30 ms 窓（HOGP の「切断直後」の値） | 切断直後の 30 秒は高く、その後は低く（HOGP） |
| 入力中のスキャン | 空きがあれば続ける | 止めて 1 秒後に再開（本家 BLE 版） |
| 名指しの広告 | すぐ接続する（型どおり） | すぐ接続（本家 BLE 版、ZMK） |
| ペアリング時の絞り込み | HID サービスの UUID か、外見の種別が HID（型どおり） | HID サービスの UUID（本家 BLE 版） |
| 失敗した接続の後始末 | 接続の世代で古い結果を捨てる、探索が 5 秒止まったら切る（`eb9a5af`、未確認） | 切断時に全部捨てる、探索が失敗したら即切断（ZMK、nRF Desktop） |

## 6. 使えないもの

- **Bluepad32**：BTstack に依存する。BTstack は持ち込まない約束（ライセンス）。
- **ESP-IDF の `esp_hidh`**：§3.7 の理由。修正入りの版が出ても、同時に複数を開く作りではない。
- **ESP-IDF の多台接続の例題**：S3 非対応。
- **Nordic の SDK のコード**：ライセンスの制限。考え方だけ参考にする。
- GPL-3.0 の中継器（Tudor3510/BLE-to-HID-Chromecast-Remote、daishuge/mi-remote-gateway）：流用しない。

## 7. 大きな選択肢（要確認）

本家 BLE 版を Zephyr ごと ESP32-S3 に載せる道がある。Zephyr が S3 の Bluetooth と USB デバイスの両方を実用水準で扱えるかは調べていない。今の ESP-IDF 構成を捨てることになるので、[ble-connect-plan.md](ble-connect-plan.md) の段階 1〜2 の結果を見てから判断する。

## 8. 未確認（要確認）

- MD600 と meteorite40 のアドレスの種類（固定か、変わるアドレスか）。機器のリセット後にアドレスが変わった記録があり、許可リストでの接続の前提になる。
- S3 のコントローラの解決リストと許可リストの実際の件数。
- `BT_NIMBLE_GATT_CACHING` が、Database Hash を持たない機器（MD600、meteorite40 が持つかは不明）で探索を省くか。
- esp-idf#18893 が G' と同じものか。
- HOGP 1.1 の採択日と 1.0 からの差分。
- Android の内部の振る舞い（AOSP のソースは取得できなかった。二次情報のみ）。
- esp32.com のフォーラムは、ボット対策で本文を読めなかった。
